# 섹션02: IAM 심화 (IAM Deep Dive)
> Well-Architected Pillar: Security
> Day: 1 | 난이도: 중급

## 개요

AWS Identity and Access Management (IAM)는 AWS 리소스에 대한 접근을 안전하게 제어하는 서비스이다. "누가" "무엇에" "어떤 조작을" "어떤 조건에서" 수행할 수 있는지를 정의하는, AWS 보안의 근간을 이루는 서비스다. 모든 AWS API 호출은 IAM에 의해 인증 및 인가되므로, IAM을 이해하지 않고는 AWS 운영이 불가능하다.

IAM의 정책 평가는 여러 정책 유형(아이덴티티 기반, 리소스 기반, 권한 경계, SCP, 세션 정책)을 조합한 복잡한 로직에 기반한다. 이들이 적절하게 구성되어 있지 않으면 보안 허점이나 권한의 과도한 부여가 발생한다. 특히 멀티 어카운트 환경에서는 SCP와 IAM 정책의 상호작용을 정확히 이해해야 한다.

또한 외부 ID 제공자와의 연계(페더레이션)는 현대 클라우드 운영에서 필수적이다. SAML 2.0에 의한 엔터프라이즈 연계, OIDC에 의한 웹 애플리케이션 연계, GitHub Actions로부터의 CI/CD 접근 등, JWT와 STS 임시 인증 정보의 구조를 깊이 이해하는 것이 요구된다.

## 핵심 개념

### IAM 정책 평가 로직

**정의:** AWS가 API 요청을 수신했을 때, 접근을 허용할지 거부할지를 결정하는 평가 알고리즘. 기본 원칙은 "명시적 Deny > 명시적 Allow > 암묵적 Deny"이다.

**평가 흐름:**

```
요청 수신
  ↓
1. 명시적 Deny가 존재하는가? → YES → 접근 거부 (종료)
  ↓ NO
2. SCP에서 허용되는가? → NO → 접근 거부 (종료)
  ↓ YES
3. 리소스 기반 정책에서 허용? → YES → 접근 허용 (종료) ※동일 어카운트 내
  ↓ NO
4. 아이덴티티 기반 정책에서 허용? → NO → 접근 거부 (종료)
  ↓ YES
5. 권한 경계에서 허용? → NO → 접근 거부 (종료)
  ↓ YES
6. 세션 정책에서 허용? → NO → 접근 거부 (종료)
  ↓ YES
7. 접근 허용
```

**소크라테스식 심화:**
> Q: "왜 명시적 Deny가 가장 강한가?"
> A: 보안의 관점에서 "금지는 항상 허용에 우선한다"가 원칙이다. 예를 들어 어떤 사용자에게 S3 전체 접근을 허용하는 정책과 특정 버킷에 대한 접근을 거부하는 정책이 모두 적용되어 있는 경우, 거부가 우선된다. 이를 통해 관리자는 "무슨 일이 있어도 절대 하게 해서는 안 되는 조작"을 확실히 차단할 수 있다.
> Q: "그렇다면 명시적 Deny가 없으면 어떻게 되는가?"
> A: 여러 정책이 겹치는 환경에서는 의도하지 않은 접근 허용이 발생할 위험이 있다. 예를 들어 팀A의 정책에서 S3 전체 버킷에 대한 접근을 허용하고, 팀B의 정책에서도 동일한 허용이 있는 경우, 특정 기밀 버킷만을 차단할 수단이 없어진다. 명시적 Deny는 이 "최후의 보루"로서 기능한다.

**현실 세계의 비유 (비IT 대상):**
> "법원과 같은 것. 명시적인 유죄 판결(Deny)이 가장 강하며, 무죄 판결(Allow)보다 우선됩니다. 판결이 없으면(암묵적), 추정 유죄(기본 Deny)입니다. 설령 10명의 증인이 무죄를 주장해도, 1건의 명시적 유죄 판결이 있으면 유죄입니다"

### 정책 유형의 전체상

**정의:** IAM에는 여러 정책 유형이 존재하며, 각각 다른 수준에서 권한을 제어한다.

| 정책 유형 | 연결 대상 | 주요 용도 |
|--------------|-----------|---------|
| **아이덴티티 기반** | 사용자, 그룹, 역할 | "이 사람에게 무엇을 허용할 것인가" |
| **리소스 기반** | S3 버킷, SQS 큐, Lambda 등 | "이 리소스에 누가 접근할 수 있는가" |
| **권한 경계** | 사용자, 역할 | "이 사람이 가질 수 있는 권한의 상한" |
| **SCP** | OU, 어카운트 | "이 어카운트 전체의 권한 상한" |
| **세션 정책** | STS AssumeRole 시 | "이 세션에만 적용되는 추가 제한" |

**권한 경계의 구조:**
권한 경계는 사용자나 역할이 가질 수 있는 최대 권한을 정의한다. 유효 권한은 아이덴티티 기반 정책과 권한 경계의 **교집합**만 해당된다.

```
유효 권한 = 아이덴티티 기반 정책 ∩ 권한 경계
```

예를 들어 아이덴티티 기반 정책에서 모든 AWS 서비스에 대한 접근을 허용해도, 권한 경계가 S3와 DynamoDB만 허용하고 있다면, 유효 권한은 S3와 DynamoDB뿐이 된다.

### JWT (JSON Web Token)

**정의:** JSON 객체로 인코딩된, 안전하게 클레임(주장)을 전달하기 위한 오픈 표준 (RFC 7519). 헤더, 페이로드, 서명의 3부분으로 구성되며, Base64URL로 인코딩되어 점(.)으로 구분하여 연결된다.

**JWT의 구조:**

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.    ← 헤더 (Header)
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6Ikpv  ← 페이로드 (Payload)
aG4gRG9lIiwiYWRtaW4iOnRydWV9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← 서명 (Signature)
```

| 부분 | 내용 | 예 |
|------|------|-----|
| **Header** | 알고리즘 정보, 토큰 타입 | `{"alg": "RS256", "typ": "JWT"}` |
| **Payload** | 클레임 (사용자 정보, 권한, 유효 기한 등) | `{"sub": "user123", "iss": "google.com", "exp": 1700000000}` |
| **Signature** | Header + Payload를 비밀 키로 서명한 것 | HMAC-SHA256 또는 RSA 서명 |

**소크라테스식 심화:**
> Q: "JWT란 무엇인가? 왜 인증에 사용되는가?"
> A: JWT는 "이 사람이 누구이며 무엇을 할 수 있는가"라는 정보를 변조 불가능한 형태로 패키징한 토큰이다. 기존 세션 방식에서는 서버가 세션 ID와 사용자 정보의 대응표를 메모리나 DB에 보유해야 했다(스테이트풀). JWT를 사용하면 토큰 자체에 사용자 정보가 포함되어 있으므로 서버는 상태를 보유할 필요가 없다(스테이트리스). 이는 마이크로서비스나 서버리스 아키텍처에서 특히 중요하다.
> Q: "JWT의 페이로드는 누구나 읽을 수 있는데, 왜 안전한가?"
> A: JWT의 페이로드는 Base64 인코딩되어 있을 뿐 암호화되어 있지 않으므로, 누구나 읽을 수 있다. 그러나 서명(Signature)이 있으므로 변조는 감지할 수 있다. 페이로드를 1글자라도 변경하면 서명이 일치하지 않게 되어 토큰은 무효로 판단된다. 즉 JWT는 "기밀성"이 아니라 "무결성"을 보장하는 구조이다. 기밀 정보를 페이로드에 포함해서는 안 된다(필요하다면 JWE: JSON Web Encryption을 사용한다).

**현실 세계의 비유 (비IT 대상):**
> "고용주가 보내는 봉인된 변조 방지 봉투와 같은 것. 봉투 표면에 '이 사람은 John, 엔지니어, 부서X 소속'이라고 적혀 있다(페이로드). 누구나 봉투를 보고 읽을 수 있지만(base64 디코딩), 고용주의 인감(전자 서명)만이 내용의 진정성을 증명합니다. 인감을 위조할 수는 없습니다. 만약 누군가가 '부서X 소속'을 '부서Y 소속'으로 고쳐 쓰면 인감이 맞지 않아 위조가 들통납니다"

### OIDC (OpenID Connect)

**정의:** OAuth 2.0 프로토콜 위에 구축된 인증 계층. 사용자의 신원 확인(인증)을 표준화하고, ID 토큰(JWT 형식)을 발행한다. OAuth 2.0이 "인가"(무엇을 할 수 있는가)만을 다루는 것에 반해, OIDC는 "인증"(누구인가)을 추가한다.

**OIDC의 흐름 (AWS와의 연계):**

```
1. 사용자 → ID 제공자 (Google 등)에 로그인
2. ID 제공자 → ID 토큰 (JWT) 발행
3. 사용자 → AWS의 STS AssumeRoleWithWebIdentity에 ID 토큰 제시
4. STS → ID 토큰 검증 (ID 제공자의 공개 키로 서명 확인)
5. STS → 임시 AWS 인증 정보 (Access Key, Secret Key, Session Token) 발행
6. 사용자 → 임시 인증 정보로 AWS 리소스에 접근
```

**소크라테스식 심화:**
> Q: "OIDC란 무엇인가? OAuth 2.0과의 차이는?"
> A: OAuth 2.0은 "이 앱에 X씨의 Google Drive 읽기를 허용한다"는 인가의 프로토콜이지만, "X씨가 정말 X씨인가"라는 인증은 정의하지 않는다. OIDC는 OAuth 2.0의 흐름 안에 ID 토큰(JWT)을 추가하여 사용자의 신원 정보를 표준적인 방법으로 취득할 수 있게 했다. AWS에서는 이 ID 토큰을 STS에 제시함으로써 외부 ID 제공자의 사용자에게 AWS 임시 인증 정보를 발행한다.
> Q: "왜 AWS 어카운트마다 사용자를 만들지 않는가?"
> A: 기업이 10개의 AWS 어카운트와 500명의 직원을 보유한 경우, 각 어카운트에 IAM 사용자를 만들면 5000개의 사용자 관리가 필요하게 된다. 비밀번호 정책, MFA, 퇴사 시 삭제를 5000개분 관리하는 것은 비현실적이다. 페더레이션을 사용하면 기존 ID 관리 시스템(Active Directory, Okta 등)의 일원 관리로 충분하다.

**현실 세계의 비유 (비IT 대상):**
> "호텔에서 정부 발행 ID를 보여주는 것과 같은 것. 호텔(AWS)은 정부(Google, GitHub 등의 ID 제공자)를 이미 신뢰하고 있습니다. 호텔 전용 새 ID를 만들 필요가 없습니다. 여권을 보여주기만 하면 체크인할 수 있고, 룸 키(임시 인증 정보)를 받을 수 있습니다. 여권의 유효성은 호텔이 정부의 데이터베이스에 문의하여 확인합니다"

### STS (Security Token Service)

**정의:** AWS STS는 임시 보안 인증 정보를 발행하는 서비스. 임시 인증 정보는 Access Key ID, Secret Access Key, Session Token의 3개 조합으로 구성되며, 지정한 유효 기한이 지나면 자동으로 무효화된다.

**주요 STS 액션:**

| 액션 | 용도 | 최대 유효 기한 |
|-----------|------|-------------|
| `AssumeRole` | 다른 역할의 권한을 취득 | 최대 12시간 (기본 1시간) |
| `AssumeRoleWithSAML` | SAML 2.0 페더레이션 | 최대 12시간 |
| `AssumeRoleWithWebIdentity` | OIDC/Web ID 페더레이션 | 최대 12시간 |
| `GetSessionToken` | MFA 인증 포함 임시 인증 정보 | 최대 36시간 |
| `GetFederationToken` | 페더레이션 사용자용 | 최대 36시간 |

**역할 체이닝 (Role Chaining):**

```
사용자A → AssumeRole(RoleB) → AssumeRole(RoleC) → AWS 리소스 접근
```

역할 체이닝의 경우, 세션의 최대 유효 기한은 **1시간**으로 제한된다(개별 역할의 최대 세션 기간 설정과 무관하게).

**소크라테스식 심화:**
> Q: "왜 영구적인 액세스 키 대신 임시 인증 정보를 사용해야 하는가?"
> A: 영구적인 액세스 키는 유출된 경우, 수동으로 로테이션할 때까지 무제한으로 접근이 가능하다. GitHub에 실수로 커밋된 액세스 키가 수 분 이내에 봇에 의해 악용되는 사례가 빈번히 보고되고 있다. 임시 인증 정보는 유효 기한이 지나면 자동으로 무효화되므로, 유출 시 리스크 윈도우가 제한된다.
> Q: "역할 체이닝에서 유효 기한이 1시간으로 제한되는 이유는?"
> A: 보안상의 이유이다. 역할 체이닝은 권한 에스컬레이션 경로가 될 수 있으므로, 각 링크에서의 유효 기한을 짧게 하여 리스크를 제한한다.

**현실 세계의 비유 (비IT 대상):**
> "오피스 빌딩의 임시 방문자 배지. 이름과 접근 레벨이 인쇄되어 있으며, 오후 5시에 만료됩니다. 상설 사원증(영구 인증 정보)과 달리, 분실해도 시간이 지나면 사용할 수 없게 됩니다. 또한 방문자 배지는 접수처(STS)에서만 발행되며, 복사할 수 없습니다"

### 최소 권한 원칙 (Principle of Least Privilege)

**정의:** 사용자나 서비스에 대해 업무 수행에 필요한 최소한의 권한만을 부여하는 원칙. 과도한 권한은 보안 리스크 증대와 감사의 복잡화를 초래한다.

**구현 접근법:**

1. **초기:** 권한 없이 시작하여 필요에 따라 추가
2. **분석:** IAM Access Analyzer를 사용하여 CloudTrail의 API 호출 로그에서 실제 사용된 권한을 분석하고, 최소 권한 정책을 자동 생성
3. **제한:** 권한 경계로 권한의 상한을 설정
4. **모니터링:** IAM Access Analyzer의 외부 접근 분석으로 의도하지 않은 외부 공유를 감지

**IAM Access Analyzer의 기능:**

| 기능 | 설명 |
|------|------|
| **외부 접근 분석** | S3 버킷, IAM 역할, KMS 키 등이 외부 어카운트에서 접근 가능한지 확인 |
| **미사용 접근 분석** | 90일 이상 사용되지 않은 권한을 감지 |
| **정책 생성** | CloudTrail의 과거 API 활동에 기반하여 최소 권한 정책을 자동 생성 |
| **정책 검증** | 정책의 문법 오류나 베스트 프랙티스 위반을 확인 |

**소크라테스식 심화:**
> Q: "왜 최소 권한이 중요한가? AdministratorAccess로 전원에게 관리자 권한을 부여하면 편하지 않은가?"
> A: 단기적으로는 편하지만, (1) 오조작 리스크: 개발자가 프로덕션 데이터베이스를 실수로 삭제할 수 있다, (2) 침해 시 피해 확대: 하나의 어카운트가 침해되면 전체 리소스에 접근 가능, (3) 컴플라이언스 위반: PCI DSS, SOC2 등의 인증 취득이 불가능해진다.
> Q: "그러나 최소 권한의 구현은 번거롭지 않은가?"
> A: IAM Access Analyzer가 이 문제를 크게 완화한다. 먼저 넓은 권한을 부여하여 운영하고, 90일 후에 CloudTrail의 실제 API 호출 로그에서 최소 권한 정책을 자동 생성할 수 있다. 처음부터 완벽을 추구하는 것이 아니라, 단계적으로 축소하는 접근법이 현실적이다.

**현실 세계의 비유 (비IT 대상):**
> "호텔 청소부에게 그날 청소 담당 객실만 여는 키를 건네는 것. 건물 전체의 마스터 키가 아닙니다. 만약 키를 잃어버려도 피해는 최소한입니다. 그리고 매일 키 배정을 재검토하고(IAM Access Analyzer), 사용하지 않는 객실의 키는 회수합니다"

### 크로스 어카운트 접근

**정의:** 한 AWS 어카운트의 IAM 프린시펄이 다른 AWS 어카운트의 리소스에 접근하는 패턴. 주로 IAM 역할의 신뢰 정책(리소스 기반 정책)을 사용하여 구현한다.

**패턴1: 역할 기반 크로스 어카운트 접근**

```
어카운트A (신뢰받는 측)                어카운트B (신뢰하는 측)
┌─────────────────────┐              ┌─────────────────────┐
│  IAM Role:          │              │  IAM 사용자/역할      │
│  CrossAccountRole   │ ←AssumeRole─ │  (arn:aws:iam::B:...) │
│                     │              │                     │
│  Trust Policy:      │              │  IAM Policy:        │
│  "Principal":       │              │  sts:AssumeRole on  │
│  {"AWS": "arn:..B"} │              │  arn:..A:role/Cross  │
└─────────────────────┘              └─────────────────────┘
```

**패턴2: 리소스 기반 정책에 의한 크로스 어카운트 접근**

S3 버킷 정책 등 리소스 기반 정책을 직접 설정하는 방법. 이 경우, 어카운트B의 사용자는 역할을 수임(AssumeRole)할 필요 없이, 자신의 인증 정보 그대로 직접 접근할 수 있다.

**중요한 차이:**
- 역할 기반: 접근 원본은 자신의 권한을 일시적으로 포기하고, 역할의 권한으로 전환
- 리소스 기반: 접근 원본은 자신의 권한을 유지한 채, 추가로 리소스에 접근 가능

### Identity Federation (SAML 2.0)

**정의:** SAML (Security Assertion Markup Language) 2.0은 엔터프라이즈 환경에서 널리 사용되는 인증 연계 표준. Active Directory Federation Services (ADFS)나 Okta 등의 ID 제공자와 AWS를 연계하여, 기업의 기존 인증 기반으로 AWS에 로그인할 수 있게 한다.

**SAML 흐름:**

```
1. 사용자 → 기업의 ID 제공자 (ADFS 등)에 로그인
2. ID 제공자 → SAML 어서션 (XML) 발행
3. 사용자 → AWS Sign-In 엔드포인트에 SAML 어서션을 POST
4. AWS STS → SAML 어서션 검증
5. AWS STS → 임시 인증 정보 발행
6. 사용자 → AWS 관리 콘솔로 리다이렉트 (또는 API 접근)
```

## 아키텍처 패턴

### 패턴1: 중앙 접근 관리 (Identity Center)

```
AWS IAM Identity Center (구 SSO)
  ├── 외부 ID 제공자 (Okta, Azure AD 등)와 연계
  ├── Permission Sets (권한 세트) 정의
  └── 어카운트 × 권한 세트 조합으로 접근 관리

사용자 → SSO 포털 → 어카운트 선택 → 역할 선택 → AWS 콘솔/CLI
```

### 패턴2: 계층적 권한 제어

```
SCP (조직 수준의 상한)
  ∩
권한 경계 (사용자/역할 수준의 상한)
  ∩
아이덴티티 기반 정책 (실제 부여하는 권한)
  =
유효 권한
```

각 레이어는 이전 레이어의 범위 내에서만 권한을 부여할 수 있다. SCP에서 금지된 조작은 아무리 IAM 정책에서 허용해도 실행할 수 없다.

### 패턴3: CI/CD 파이프라인의 OIDC 연계

```
GitHub Actions
  ↓ (OIDC 토큰)
AWS STS AssumeRoleWithWebIdentity
  ↓ (임시 인증 정보)
AWS 리소스에 배포
```

GitHub Actions의 워크플로우에서는 영구적인 액세스 키를 시크릿에 저장하는 대신, OIDC 제공자로서 GitHub를 신뢰하고, 워크플로우 실행 시 임시 인증 정보를 취득한다. 이를 통해 인증 정보의 유출 리스크가 제로가 된다.

## SAA 시험 포인트

- **정책 평가 순서:** 명시적 Deny > SCP > 리소스 기반 정책 > 아이덴티티 기반 정책 > 권한 경계 > 세션 정책 > 암묵적 Deny
- **리소스 기반 정책의 특수성:** 동일 어카운트 내에서는 리소스 기반 정책의 Allow만으로 접근이 허용된다(아이덴티티 기반 정책 불필요). 크로스 어카운트에서는 양쪽 모두 필요.
- **권한 경계는 접근을 부여하지 않는다.** 상한을 설정할 뿐이다. 실제 접근에는 아이덴티티 기반 정책이 필요.
- **역할 체이닝(Role Chaining)에서는 세션 유효 기한이 최대 1시간**으로 제한된다.
- **IAM Access Analyzer의 정책 생성**은 CloudTrail의 로그에 기반하므로, CloudTrail이 활성화되어 있지 않으면 기능하지 않는다.
- **SAML 2.0 페더레이션**은 엔터프라이즈 대상 (ADFS, Okta), **Web Identity / OIDC**는 모바일 앱이나 웹 앱 대상 (Google, Facebook, Amazon).
- **외부 ID (ExternalId):** 서드 파티에 크로스 어카운트 접근을 허용할 때, "혼동된 대리인 (Confused Deputy)" 문제를 방지하기 위해 사용하는 조건 키.
- **MFA 조건:** `aws:MultiFactorAuthPresent` 조건 키로 MFA 인증 완료 세션에만 접근을 제한할 수 있다.
- **SCP는 루트 어카운트의 IAM 사용자에게도 적용되지만**, 루트 어카운트 자체(관리 어카운트)에는 SCP가 적용되지 않는다.
