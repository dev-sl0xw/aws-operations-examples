# 섹션08: 이벤트 구동 아키텍처 & 관측 가능성
> Well-Architected Pillar: Operational Excellence
> Day: 2 | 난이도: 중급

## 개요

이벤트 구동 아키텍처(EDA: Event-Driven Architecture)는 시스템 컴포넌트 간의 통신을 이벤트(상태 변화의 통지)로 수행하는 아키텍처 패턴이다. AWS에서는 EventBridge가 중앙 이벤트 버스로 기능하며, AWS 서비스, SaaS 애플리케이션, 커스텀 애플리케이션으로부터의 이벤트를 통합적으로 라우팅한다.

관측 가능성의 관점에서는 AWS X-Ray가 분산 트레이싱을 제공하여 마이크로서비스 간의 리퀘스트 플로우를 가시화한다. SNS(Simple Notification Service)는 Pub/Sub 메시징 서비스로서 이벤트 통지의 팬아웃(1대다 배포)을 실현한다. 이러한 서비스를 조합함으로써 「무엇이 일어났는가」를 감지하고(EventBridge), 「왜 일어났는가」를 추적하며(X-Ray), 「누구에게 전달하는가」를 제어하는(SNS) 통합적인 운영 기반을 구축할 수 있다.

SAA 시험에서는 EventBridge의 이벤트 패턴과 타겟의 조합, X-Ray의 세그먼트/서브세그먼트 개념, SNS의 팬아웃 패턴, 그리고 이들을 통합한 이벤트 구동의 자동화·관측 가능성 아키텍처가 출제된다. 특히 EventBridge와 CloudWatch Events의 관계(EventBridge는 CloudWatch Events의 후속)도 이해해 둘 필요가 있다.

## 핵심 개념

### 이벤트 구동 아키텍처 (Event-Driven Architecture)

**정의:** 시스템의 상태 변화(이벤트)를 감지하여 그에 대한 액션(반응)을 자동적으로 실행하는 아키텍처. 이벤트 프로듀서(발행자)와 이벤트 컨슈머(소비자)가 느슨한 결합으로 접속되며, 이벤트 버스(중개자)를 통해 통신한다. 폴링 방식(정기적인 확인)에 대한 푸시 방식(변화 시의 통지).

**소크라테스식 심화:**
> Q: "이벤트 구동 아키텍처란 무엇인가? 왜 중요한가?"
> A: 인감 센서가 달린 조명이 있는 집을 상상해보자. 아무도 스위치를 누르지 않는다(폴링하지 않는다). 무언가가 일어나면(사람이 입실하는 이벤트) 조명이 자동으로 반응한다. EventBridge는 집 안의 센서(이벤트 소스)와 액션(타겟)을 연결하는 중추 신경계이다. 폴링 방식은 정기적으로 스위치를 확인하러 가는 비효율적인 방법이다. 이벤트 구동의 이점: (1) 실시간성: 변화가 일어난 순간에 대응 (2) 느슨한 결합: 프로듀서와 컨슈머가 서로를 알 필요가 없다 (3) 확장성: 컨슈머를 독립적으로 스케일 가능 (4) 비용 효율: 불필요한 폴링 처리가 없다.
> Q: "그렇다면 이벤트 구동이 아니면 어떻게 되는가?"
> A: 모든 컴포넌트가 정기적으로 「뭔가 바뀌었나?」라고 확인하는 폴링 방식이 된다. 100개의 서비스가 서로 폴링하면 통신량은 지수 함수적으로 증대한다. 또한 폴링 간격만큼 반응이 지연된다. 1분 간격의 폴링에서는 최대 1분의 지연이 발생한다. 이벤트 구동이면 상태 변화의 순간에 통지가 도착한다. 더 나아가 폴링에서는 직접적인 의존 관계가 생겨, 하나의 서비스 변경이 다른 것에 영향을 미치는 밀결합이 된다.

**현실 세계의 비유 (비IT 대상):**
> "신문 정기 구독(폴링) vs 스마트폰의 푸시 알림(이벤트 구동). 정기 구독은 매일 아침 정해진 시간에 도착하지만 속보 뉴스는 다음 아침까지 기다려야 한다. 푸시 알림은 중요한 뉴스가 발생한 순간에 도착한다. EventBridge는 스마트폰의 알림 센터처럼 다양한 앱(AWS 서비스)으로부터의 알림을 일원 관리한다."

### EventBridge의 구성 요소

**정의:** EventBridge는 서버리스 이벤트 버스 서비스로, 이벤트 버스(Event Bus), 규칙(Rules), 타겟(Targets)의 3가지 주요 컴포넌트로 구성된다. 이벤트 버스는 이벤트의 수신구, 규칙은 이벤트의 필터링 조건, 타겟은 액션의 실행 대상이다.

**소크라테스식 심화:**
> Q: "EventBridge의 이벤트 버스의 종류와 사용 구분은?"
> A: (1) **Default Event Bus:** AWS 서비스로부터의 이벤트를 수신한다. EC2의 상태 변화, S3의 오브젝트 조작, GuardDuty의 감지 결과 등이 여기에 흐른다. 자동적으로 존재하며 삭제할 수 없다. (2) **Custom Event Bus:** 커스텀 애플리케이션으로부터의 이벤트를 수신한다. PutEvents API로 이벤트를 송신. 마이크로서비스 간의 이벤트 통신에 사용. (3) **Partner Event Bus:** SaaS 파트너(Datadog, PagerDuty, Zendesk 등)로부터의 이벤트를 수신한다. AWS가 사전 통합 완료된 파트너 서비스로부터의 이벤트를 네이티브로 처리할 수 있다.
> Q: "EventBridge의 규칙(이벤트 패턴)은 어떻게 기능하는가?"
> A: JSON 기반의 패턴 매칭. 이벤트의 구조(source, detail-type, detail 등)에 대해 조건을 지정한다. 예를 들어 「source: aws.ec2」이고 「detail-type: EC2 Instance State-change Notification」이며 「detail.state: terminated」의 패턴을 설정하면, EC2 인스턴스의 종료 이벤트만 캐치한다. 수치 비교(greater-than), 접두사 매치, 와일드카드도 사용 가능.

**현실 세계의 비유 (비IT 대상):**
> "우체국 시스템. 이벤트 버스 = 우체국 창구(편지를 접수한다). 규칙 = 분류 기준(수신지의 도시, 속달/보통의 구별). 타겟 = 배달 대상(각 지역의 배송 센터). 편지(이벤트)가 도착하면 분류 기준(규칙)에 따라 적절한 배송지(타겟)에 자동으로 분배된다."

### EventBridge Archive & Replay

**정의:** EventBridge의 Archive 기능은 이벤트를 보존하고, Replay 기능으로 과거의 이벤트를 재실행할 수 있다. 디버그, 테스트, 장애 복구 시에 과거의 이벤트를 정확히 재현하는 것이 가능. 보존 기간과 필터 패턴을 지정하여 아카이브를 생성한다.

**소크라테스식 심화:**
> Q: "이벤트의 아카이브와 리플레이는 왜 중요한가?"
> A: 운영 환경에서 장애가 발생하여 일부 이벤트가 올바르게 처리되지 않은 경우를 생각해보자. 수정 후에 아카이브에서 이벤트를 리플레이함으로써 잃어버린 처리를 복구할 수 있다. 또한 새로운 이벤트 처리 로직의 개발 시에 과거의 운영 이벤트를 테스트 환경에 리플레이하여 테스트할 수 있다. 타임 트래블 디버깅이라고도 불린다.
> Q: "아카이브의 비용을 최적화하려면?"
> A: 필터 패턴을 사용하여 필요한 이벤트만 아카이브한다. 전체 이벤트를 아카이브하면 스토리지 비용이 막대해진다. 예를 들어 「detail-type: Order Placed」의 이벤트만 아카이브하고, 헬스 체크 등의 빈번하고 낮은 중요도의 이벤트는 제외한다. 보존 기간도 적절히 설정한다.

**현실 세계의 비유 (비IT 대상):**
> "감시 카메라의 녹화와 재생. 사건(장애)이 일어났을 때 녹화(아카이브)를 되감아(리플레이) 무엇이 일어났는지를 정확히 확인할 수 있다. 모든 카메라의 전 시간대를 보존하면 막대한 스토리지가 필요하므로, 중요한 구역만 녹화하는 것과 같다."

### 분산 트레이싱 (AWS X-Ray)

**정의:** X-Ray는 분산 애플리케이션의 리퀘스트 플로우를 추적·가시화하는 서비스. 세그먼트(Segment)는 서비스의 엔트리 포인트, 서브세그먼트(Subsegment)는 다운스트림 호출(API, DB, 외부 서비스 등)을 나타낸다. 트레이스 ID(Trace ID)로 엔드투엔드의 리퀘스트를 일의로 식별한다.

**소크라테스식 심화:**
> Q: "분산 트레이싱이란 무엇인가? 왜 필요한가?"
> A: FedEx의 화물 추적과 같은 것. 화물(리퀘스트)은 복수의 분류 시설(마이크로서비스)을 통과한다. X-Ray는 화물의 어디서든 추적할 수 있는 하나의 추적 번호(Trace ID)를 부여하고, 어느 시설에서 지연이 일어났는지를 보여준다. 추적 번호가 없으면 화물이 어디에서 멈춰있는지 전혀 알 수 없다. 마이크로서비스 아키텍처에서는 하나의 리퀘스트가 10개 이상의 서비스를 통과하는 것이 있다. 어느 서비스에서 에러나 지연이 발생하고 있는지를 특정하려면, 리퀘스트 전체를 횡단적으로 추적하는 구조가 불가결하다.
> Q: "세그먼트와 서브세그먼트의 차이는 무엇인가?"
> A: 세그먼트는 서비스(Lambda 함수, EC2 위의 애플리케이션 등) 전체의 처리를 나타내는 큰 상자. 서브세그먼트는 그 서비스 내에서의 다운스트림 호출(DynamoDB로의 쿼리, 외부 API로의 HTTP 리퀘스트 등)을 나타내는 작은 상자. 세그먼트 안에 서브세그먼트가 네스트되는 구조. 이에 의해 「Lambda 함수 A는 500ms」→ 「그 중 DynamoDB 호출이 300ms」→ 「나머지 200ms는 자체 처리」와 같이 지연의 병목 현상을 정확히 특정할 수 있다.

**현실 세계의 비유 (비IT 대상):**
> "병원에서의 진료 프로세스 추적. 접수(API Gateway) → 문진(Lambda A) → 혈액 검사(DynamoDB) → X-ray 촬영(S3) → 의사 진단(Lambda B) → 회계(Lambda C). 각 단계의 소요 시간을 기록하여 'X-ray 촬영에 30분이 걸리고 있다(병목 현상)'를 특정한다. 환자 ID가 Trace ID에 해당한다."

### X-Ray의 Annotation과 Metadata

**정의:** Annotation은 키-밸류 형식의 데이터로, 인덱스가 생성되어 검색 가능. Metadata도 마찬가지로 키-밸류 형식이지만, 인덱스되지 않아 검색 불가. Annotation은 필터 식에서의 검색에 사용하고, Metadata는 디버그용 상세 정보를 저장한다.

**소크라테스식 심화:**
> Q: "Annotation과 Metadata의 사용 구분은?"
> A: Annotation은 도서관의 도서 카드와 같은 것. 「저자명: 김철수」 「장르: SF」와 같이 검색에 사용할 수 있는 키워드. Metadata는 책의 내용 자체로, 상세하지만 색인에서는 검색할 수 없다. X-Ray에서는 Annotation에 「customerId: C123」 「region: ap-northeast-1」을 설정하면, 「customerId = C123의 트레이스를 전부 검색」이 가능. Metadata에는 리퀘스트 바디나 리스폰스 상세를 저장하고, 개별 트레이스를 열었을 때 확인한다.
> Q: "Annotation의 수에 제한이 있는가?"
> A: 세그먼트당 최대 50개의 Annotation. 키는 영숫자와 언더스코어만. 검색 비용에 직결되므로, 정말로 검색에 필요한 필드만 Annotation으로 한다. 모든 데이터를 Annotation으로 하면 인덱스의 사이즈와 비용이 증대한다.

**현실 세계의 비유 (비IT 대상):**
> "여행 가방에 붙이는 태그. Annotation = 공항에서 기계가 읽는 바코드 태그(검색 가능, 목적지·편명). Metadata = 여행 가방 안의 내용물 리스트(열어봐야 보이며, 검색 불가). 공항 시스템은 태그(Annotation)로 짐을 추적하지만, 내용물(Metadata)은 개별적으로 확인해야 한다."

### X-Ray 샘플링

**정의:** X-Ray가 전체 리퀘스트가 아닌 일정 비율의 리퀘스트만 트레이싱하는 구조. 기본적으로 매초 처음 1리퀘스트와 추가 리퀘스트의 5%를 샘플링한다. 커스텀 샘플링 규칙으로 특정 조건(URL 경로, HTTP 메소드 등)에 기반하여 샘플링 비율을 변경할 수 있다.

**소크라테스식 심화:**
> Q: "왜 전체 리퀘스트를 트레이싱하지 않는가?"
> A: 품질 관리의 샘플 검사와 같은 원리. 전 제품(리퀘스트)을 검사하면 비용과 시간이 너무 많이 든다. 일정 비율만 상세히 검사(트레이스)하고 전체 품질을 추정한다. 매초 1만 리퀘스트의 애플리케이션에서 전체 트레이스하면, X-Ray로의 전송 데이터량, 스토리지 비용, 네트워크 대역폭이 막대해진다. 5%의 샘플링으로도 통계적으로 충분한 가시성을 얻을 수 있다.
> Q: "샘플링 비율을 커스터마이즈하는 경우는?"
> A: (1) 결제 API 등 중요한 엔드포인트는 샘플링 비율을 높이고(예: 50%) (2) 헬스 체크 엔드포인트는 샘플링 비율을 낮추거나(예: 0.1%) 제외 (3) 에러가 발생한 리퀘스트는 100% 트레이스(에러 샘플링) (4) 운영 환경은 낮은 샘플링, 스테이징 환경은 높은 샘플링. X-Ray daemon 측에서 규칙을 동적으로 변경할 수 있으며 애플리케이션의 재배포는 불필요.

**현실 세계의 비유 (비IT 대상):**
> "고속도로의 교통량 조사. 전 차량을 개별 추적하는 것은 불가능하므로, 일정 비율(100대에 5대)의 차에 GPS 트래커를 부착하여 전체 교통 패턴을 추정한다. 정체가 발생하기 쉬운 구간(중요 엔드포인트)은 트래커의 비율을 늘린다."

### SNS (Simple Notification Service)

**정의:** SNS는 풀매니지드 Pub/Sub(발행/구독) 메시징 서비스. 토픽(Topic)에 메시지를 발행하면 그 토픽을 구독하고 있는 모든 구독자에게 메시지가 배포된다. Standard Topic(높은 스루풋, 최소 1회 배포)과 FIFO Topic(순서 보장, 정확히 1회 배포)의 2종류가 있다.

**소크라테스식 심화:**
> Q: "SNS의 팬아웃 패턴이란 무엇인가?"
> A: TV 생방송과 같은 것. 하나의 방송국(SNS 토픽)이 송신하면 모든 TV(SQS 큐, Lambda 함수, 이메일 주소 등)가 동시에 수신한다. 각 TV는 독립적으로 프로그램을 처리할 수 있다. 예를 들어 주문 이벤트를 SNS 토픽에 발행하면 (1) SQS 큐 A → 재고 관리 서비스 (2) SQS 큐 B → 배송 수배 서비스 (3) Lambda → 고객 통지 메일 (4) Kinesis → 분석 기반에 동시 배포된다. 각 서비스는 독립적으로 처리할 수 있으며, 하나의 서비스 장애가 다른 것에 영향을 미치지 않는다.
> Q: "SNS의 메시지 필터링은 왜 중요한가?"
> A: 필터링이 없으면 모든 구독자가 전체 메시지를 수신하고, 자신과 관계없는 메시지를 버리는 처리가 필요하다. 이는 불필요한 컴퓨팅 리소스의 소비이다. SNS의 필터 정책을 사용하면 구독 레벨에서 메시지를 사전 필터링할 수 있다. 예를 들어 「order_type: express」의 속성을 가진 메시지만 특급 배송 서비스의 SQS 큐에 배포한다. 이에 의해 각 서비스는 관련 있는 메시지만 수신하고 처리 효율이 향상된다.

**현실 세계의 비유 (비IT 대상):**
> "학교의 교내 방송. SNS 토픽 = 방송 시스템. 전교 방송(필터 없음)은 전 교실에 도달한다. 학년별 방송(필터 있음)은 해당 학년의 교실에만 도달한다. 각 교실(구독자)은 수신한 방송을 독립적으로 처리(대응)한다."

### SNS Standard vs FIFO Topic

**정의:** Standard Topic은 높은 스루풋(거의 무제한)으로 최소 1회(at-least-once)의 배포를 보장하지만, 순서는 보장하지 않는다. FIFO Topic은 정확히 1회(exactly-once)의 배포와 순서 보장을 제공하지만, 300메시지/초(배치 없음) 또는 3000메시지/초(배치 있음)의 스루풋 제한이 있다.

**소크라테스식 심화:**
> Q: "at-least-once와 exactly-once의 차이는 무엇인가?"
> A: at-least-once(최소 1회)는 같은 메시지가 2회 이상 도착할 가능성이 있다. 우편으로 예를 들면, 중요한 편지를 만약을 위해 2통 보내는 것과 같다. 수신자는 중복을 처리할 필요가 있다(멱등성의 구현). exactly-once(정확히 1회)는 반드시 1회만 도착한다. 은행 송금으로 예를 들면, 같은 송금이 2회 실행되면 큰 문제가 된다. FIFO Topic은 중복 제거 ID(MessageDeduplicationId)와 메시지 그룹 ID(MessageGroupId)로 순서와 중복 제거를 관리한다.
> Q: "어느 쪽을 선택해야 하는가?"
> A: 대부분의 경우 Standard Topic으로 충분하다. 컨슈머 측에서 멱등성을 구현하면 중복은 문제가 되지 않는다. FIFO가 필요한 것은 금융 거래처럼 순서와 일회성이 엄격히 필요한 경우뿐이다. FIFO Topic의 구독자는 현재 SQS FIFO 큐만(Lambda 직접 호출은 불가)이라는 제약도 있다.

**현실 세계의 비유 (비IT 대상):**
> "Standard = 일반 우편. 가끔 2통 도착하기도 하고, 순서가 바뀌기도 한다. 하지만 대량의 우편을 고속으로 처리할 수 있다. FIFO = 등기 우편. 반드시 1통만, 보낸 순서대로 도착한다. 다만 처리 속도는 느리다. 용도에 따라 사용을 구분한다."

### 이벤트 구동 자동화 패턴

**정의:** AWS 서비스의 이벤트를 트리거로 하여 운영 태스크를 자동화하는 패턴. EventBridge의 규칙으로 이벤트를 감지하고, Lambda, Step Functions, SSM 등의 타겟으로 자동 대응을 실행한다. 수동 오퍼레이션의 배제와 MTTR(평균 복구 시간)의 단축이 목적.

**소크라테스식 심화:**
> Q: "이벤트 구동 자동화의 전형적인 유스 케이스는?"
> A: (1) **EC2 상태 변화 → Slack 통지:** EC2 인스턴스가 terminated가 되면 EventBridge가 캐치하고, Lambda 경유로 Slack에 통지. 의도하지 않은 종료를 즉시 감지. (2) **S3 업로드 → 처리 파이프라인:** S3에 파일이 업로드되면 EventBridge가 감지하고, Step Functions로 이미지 리사이즈 → 메타데이터 추출 → DynamoDB 등록의 파이프라인을 기동. (3) **AWS Health → 자동 복구:** AWS 인프라의 장애 통지를 EventBridge가 수신하고, Lambda 경유로 SSM Run Command를 실행하여 영향을 받은 인스턴스를 자동으로 마이그레이션. (4) **GuardDuty → 보안 대응:** 부정 접근 감지 → 자동으로 보안 그룹을 변경하여 접근을 차단.
> Q: "자동화를 너무 많이 하는 것의 리스크는 있는가?"
> A: 있다. 자동 복구 로직에 버그가 있으면 문제를 악화시킬 가능성이 있다. 예를 들어 일시적인 에러로 자동으로 인스턴스를 종료·재시작하는 로직이, 근본 원인인 데이터베이스 장애 때문에 무한 루프에 빠질 가능성이 있다. 베스트 프랙티스는 먼저 「감지와 통지」의 자동화부터 시작하고, 충분한 테스트 후에 「복구의 자동화」로 진행하는 것. Circuit Breaker(회로 차단기) 패턴의 구현도 중요.

**현실 세계의 비유 (비IT 대상):**
> "스마트 홈의 자동화. 연기 감지기(EventBridge)가 연기를 감지 → 자동으로 스프링클러 기동(Lambda) → 소방서에 통보(SNS) → 이웃에 대피 통지(Slack). 전부 사람 손을 거치지 않고 자동으로 연쇄 실행된다. 다만, 토스트의 연기로 매번 스프링클러가 작동하면 곤란하므로, 적절한 감도 설정(규칙의 정밀도)이 중요."

### 통합 패턴: EventBridge → SNS → Lambda → SSM

**정의:** AWS 서비스의 이벤트를 EventBridge로 감지하고, SNS로 통지를 팬아웃하며, Lambda로 처리 로직을 실행하고, SSM Run Command로 대상 인스턴스에 조작을 실행하는 통합 자동화 패턴.

**소크라테스식 심화:**
> Q: "이 통합 패턴의 각 서비스의 역할은?"
> A: EventBridge = 「무엇이 일어났는지를 감지하는 센서」. EC2의 상태 변화, 스케줄 이벤트 등을 감지. SNS = 「누구에게 전달할지를 관리하는 통지 시스템」. 운영팀으로의 메일, Slack 채널, 자동 복구 Lambda 등에 동시 배포. Lambda = 「무엇을 할지를 결정하는 판단 엔진」. 이벤트의 내용을 분석하고 적절한 대응을 결정. SSM Run Command = 「대상 서버에서 실제로 명령을 실행하는 손과 발」. Lambda의 판단에 기반하여 EC2 인스턴스에서 스크립트를 실행.
> Q: "이 통합 패턴을 구축할 때의 주의점은?"
> A: (1) Lambda 함수의 에러 핸들링: 실패 시의 리트라이 설정과 Dead Letter Queue(DLQ)의 설정 (2) IAM 역할의 최소 권한: 각 서비스에 필요 최소한의 권한만 부여 (3) SNS의 메시지 필터링: 불필요한 메시지를 각 컨슈머에게 보내지 않음 (4) EventBridge 규칙의 정밀도: 너무 넓은 패턴은 의도하지 않은 이벤트를 캐치함 (5) SSM Run Command의 멱등성: 같은 명령이 2번 실행되어도 문제가 없는 것을 보장.

**현실 세계의 비유 (비IT 대상):**
> "119 신고 시스템. 화재 감지기(EventBridge)가 화재를 감지 → 소방 본부(SNS)에 통보 → 소방 본부가 (1) 소방차(Lambda+SSM)를 출동 (2) 경찰(메일 통지)에 연락 (3) 병원(다른 Lambda)에 수용 준비를 의뢰. 하나의 이벤트가 복수의 대응을 동시에 기동한다."

## SAA 시험 포인트

1. **EventBridge vs CloudWatch Events:** EventBridge는 CloudWatch Events의 후속·상위 호환. 시험에서는 EventBridge로 통일되고 있지만, CloudWatch Events의 명칭도 등장한다. 같은 API 백엔드.

2. **EventBridge의 이벤트 패턴:** JSON 기반의 패턴 매칭. source, detail-type, detail 필드로 필터링. 스케줄 식(cron, rate)으로 정기 실행도 가능.

3. **EventBridge의 타겟:** 하나의 규칙에 최대 5개의 타겟을 설정 가능. Lambda, SNS, SQS, Step Functions, SSM Run Command, API Destinations(HTTP API) 등.

4. **X-Ray의 액티브 트레이싱 vs 패시브 트레이싱:** 액티브 = 서비스 자체가 X-Ray SDK로 트레이스 데이터를 생성. 패시브 = 상류의 서비스로부터 트레이스 헤더를 받은 경우에만 트레이스. Lambda 함수는 콘솔에서 Active Tracing을 활성화하기만 하면 사용 가능.

5. **X-Ray SDK의 대응 서비스:** Lambda(내장 지원), API Gateway, ECS/EKS, EC2(X-Ray daemon 필요), Elastic Beanstalk(설정에서 활성화).

6. **SNS + SQS 팬아웃:** 1대다의 메시지 배포 패턴으로 빈출. 「주문 처리에서 복수의 서비스에 이벤트를 동시 배포하고 싶다」→ SNS + SQS 팬아웃.

7. **SNS 메시지 필터링:** 구독 단위로 필터 정책을 설정. 불필요한 메시지의 처리를 배제하여 비용과 효율을 최적화. MessageAttributes에 기반한 필터링.

8. **EventBridge Schema Registry:** 이벤트의 구조(스키마)를 자동 감지·등록하는 기능. 스키마에서 코드 바인딩을 자동 생성할 수 있어 개발 효율이 향상.

9. **X-Ray 샘플링 규칙:** 기본(리저버 = 1/초, 비율 = 5%). 커스텀 규칙으로 URL 경로나 HTTP 메소드에 기반하여 샘플링 비율을 변경 가능. 콘솔에서 동적으로 변경 가능(애플리케이션 재배포 불필요).

10. **Dead Letter Queue (DLQ):** EventBridge의 타겟으로의 배포가 실패한 경우에 SQS DLQ에 이벤트를 퇴피. SNS의 구독 배포 실패 시에도 SQS DLQ를 설정 가능. DLQ의 설정은 장애 내성의 중요한 요소.

   - X-Ray 콘솔에서 Service Map과 트레이스의 확인
   - Annotation의 추가와 검색 실행

4. **SNS 팬아웃의 구축:**
   - SNS 토픽의 작성
   - SQS 큐(2개)와 Lambda를 구독자로 등록
   - 메시지 필터 정책의 설정
   - 테스트 메시지의 발행과 각 구독자에서의 수신 확인

5. **통합 패턴의 구축:**
   - EventBridge → SNS → Lambda → CloudWatch Logs의 플로우 구축
   - 에러 핸들링(DLQ)의 설정
   - EventBridge Archive의 작성과 Replay의 테스트

## Well-Architected 체크리스트

### Operational Excellence (운영 우수성)

- [ ] 운영 이벤트(인스턴스 장애, 디플로이 완료 등)가 EventBridge로 감지되고 있는가
- [ ] 중요한 이벤트에 대해 자동 통지(SNS → Slack/Email)가 설정되어 있는가
- [ ] 이벤트 구동의 자동 복구가 구현되어 있는가(최소한 감지와 통지는 자동화)
- [ ] X-Ray로 주요 리퀘스트 플로우가 트레이싱되고 있는가
- [ ] X-Ray의 샘플링 규칙이 적절히 설정되어 있는가(비용 vs 가시성)
- [ ] X-Ray의 Annotation으로 중요한 검색 키(customerId 등)가 설정되어 있는가
- [ ] SNS의 메시지 필터링으로 불필요한 메시지 처리를 배제하고 있는가
- [ ] EventBridge의 Archive & Replay로 디버그와 리커버리가 가능한가
- [ ] Dead Letter Queue(DLQ)가 설정되어 배포 실패 이벤트가 보전되고 있는가
- [ ] 이벤트 패턴이 적절히 한정되어 불필요한 이벤트의 처리를 피하고 있는가
- [ ] EventBridge Schema Registry로 이벤트 스키마가 관리되고 있는가
- [ ] 자동화의 에러 핸들링과 Circuit Breaker(무한 루프 방지)가 구현되어 있는가
