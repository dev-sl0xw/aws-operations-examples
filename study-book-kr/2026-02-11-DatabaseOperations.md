# 섹션15: 데이터베이스 운영 (Database Operations)
> Well-Architected Pillars: Reliability, Performance Efficiency, Cost Optimization
> Day: 4 | 난이도: 중급~상급

## 개요

AWS의 데이터베이스 서비스는 애플리케이션의 핵심을 이루는 데이터 영속화 레이어이다. 관계형 데이터베이스로서 Amazon RDS와 Amazon Aurora가, NoSQL 데이터베이스로서 Amazon DynamoDB가 제공되고 있다. 각각 다른 데이터 모델, 스케일링 특성, 가용성 아키텍처를 가지며, 워크로드의 요건에 따라 적절한 서비스를 선정하는 것이 아키텍트 설계의 첫걸음이 된다.

RDS는 MySQL, PostgreSQL, MariaDB, Oracle, SQL Server의 5가지 엔진을 지원하며, 패치 적용, 백업, 레플리케이션과 같은 운영 태스크를 자동화하는 풀매니지드 서비스이다. Aurora는 MySQL/PostgreSQL 호환의 독자 엔진이며, 3개의 AZ에 6카피를 분산 저장하는 스토리지 아키텍처에 의해 기존 RDS를 넘어서는 가용성과 퍼포먼스를 실현한다. DynamoDB는 키-밸류형의 NoSQL 데이터베이스이며, 임의의 스케일에서 밀리초 수준의 레이턴시를 제공하고, 서버리스 아키텍처와의 친화성이 극히 높다.

데이터베이스 운영에 있어서는 고가용성 (Multi-AZ), 읽기 스케일링 (Read Replicas), 퍼포먼스 모니터링 (Performance Insights), 접속 관리 (RDS Proxy), 백업·복구 전략, 그리고 데이터베이스 마이그레이션 (DMS/SCT)을 포괄적으로 이해할 필요가 있다. 이러한 지식은 SAA 시험에서 빈출이며, Well-Architected Framework의 신뢰성, 퍼포먼스 효율, 비용 최적화의 3가지 기둥에 깊이 관련된다.

## 핵심 개념

### Amazon RDS (Relational Database Service)

**정의:** AWS가 제공하는 풀매니지드 관계형 데이터베이스 서비스. MySQL, PostgreSQL, MariaDB, Oracle, SQL Server의 5가지 엔진을 지원한다. OS/DB 엔진의 패치 적용, 자동 백업, Multi-AZ 페일오버 등의 운영 태스크를 자동화하여, 사용자는 애플리케이션 개발에 집중할 수 있다.

**소크라테스식 심화:**
> Q: "RDS란 무엇인가? EC2에 데이터베이스를 직접 설치하는 경우와 무엇이 다른가?"
> A: RDS는 「매니지드」서비스이며, AWS가 데이터베이스의 인프라 운영을 대행한다. EC2에 직접 MySQL을 설치하는 경우, OS의 패치 적용, 데이터베이스 엔진의 업그레이드, 백업 설정, 레플리케이션 구축, 페일오버 설계를 전부 스스로 수행할 필요가 있다. RDS에서는 이것들이 자동화 또는 원클릭으로 설정 가능하다. 다만, RDS에서는 OS에 대한 SSH 액세스는 불가능하다 (커스텀 RDS 제외). OS 수준의 튜닝이나 커스텀 플러그인이 필요한 경우는 EC2상의 자체 관리가 선택지가 된다.
> Q: "RDS의 인스턴스 클래스와 스토리지 타입은 어떻게 선정하는가?"
> A: 인스턴스 클래스는 CPU/메모리의 조합이며, db.t3 (버스트), db.r6g (메모리 최적화), db.m6g (범용) 등이 있다. 개발 환경에는 db.t3, 운영 환경의 OLTP 워크로드에는 db.r6g가 권장된다. 스토리지 타입은 gp3 (범용 SSD), io1/io2 (프로비전드 IOPS SSD), magnetic (구세대 HDD)의 3종류가 있다. gp3는 베이스라인 3,000 IOPS와 125 MB/s가 포함되어 비용 효율이 가장 높다. io1/io2는 고 IOPS가 필요한 워크로드용으로, 최대 256,000 IOPS (io2 Block Express)까지 설정 가능하다.

**현실 세계의 비유 (비IT 대상):**
> "RDS는 임대 아파트와 같은 것. 건물의 관리 (OS)나 공용부의 수선 (패치 적용)은 관리 회사 (AWS)가 해준다. 입주자 (개발자)는 방 안의 내용 (데이터베이스의 설계나 쿼리)에 집중하면 된다. 다만, 벽을 부수고 개조하는 것 (OS 수준의 커스터마이징)은 할 수 없다"

**RDS 인스턴스 클래스 비교:**

| 카테고리 | 클래스 예 | 특징 | 유스 케이스 |
|---------|---------|------|-----------|
| **버스트** | db.t3, db.t4g | CPU 크레딧 방식, 저비용 | 개발·테스트, 소규모 워크로드 |
| **범용** | db.m6g, db.m7g | 균형 잡힌 CPU/메모리 | 중규모의 운영 워크로드 |
| **메모리 최적화** | db.r6g, db.r7g | 고메모리 용량 | 대규모 OLTP, 캐시 집약형 |
| **메모리 최적화 (확장)** | db.x2g | 최대 메모리 | SAP HANA, 대규모 인메모리 처리 |

**RDS 스토리지 타입 비교:**

| 스토리지 타입 | IOPS (최대) | 스루풋 (최대) | 용량 | 특징 |
|-------------|------------|-------------|------|------|
| **gp3** | 16,000 | 1,000 MB/s | 20 GiB - 64 TiB | IOPS/스루풋 독립 설정, 권장 |
| **io1** | 64,000 | 1,000 MB/s | 100 GiB - 64 TiB | 고 IOPS 요건, Multi-AZ io1 |
| **io2 Block Express** | 256,000 | 4,000 MB/s | 100 GiB - 64 TiB | 최고 성능, 서브밀리초 레이턴시 |
| **magnetic** | — | — | 20 GiB - 1 TiB | 구세대, 비권장 |

### RDS Multi-AZ

**정의:** 프라이머리 DB 인스턴스의 동기 레플리카를 다른 AZ에 자동 배치하는 고가용성 구성. 프라이머리 인스턴스의 장애 시 60~120초에 자동 페일오버가 실행된다. DNS 엔드포인트는 변경되지 않으므로, 애플리케이션 측의 코드 변경은 불필요하다.

**소크라테스식 심화:**
> Q: "Multi-AZ란 무엇인가? 왜 필요한가?"
> A: Multi-AZ는 데이터베이스의 「보험」이다. 프라이머리 DB가 존재하는 AZ에 장애가 발생한 경우, 다른 AZ의 스탠바이 레플리카가 자동으로 프라이머리로 승격된다. 이 프로세스는 DNS 엔드포인트의 전환에 의해 이루어지므로, 애플리케이션은 같은 접속처로 계속 동작한다. 동기 레플리케이션에 의해 프라이머리에의 쓰기는 스탠바이에도 즉시 반영되므로, 페일오버 시의 데이터 손실은 제로이다 (RPO = 0).
> Q: "Multi-AZ와 Read Replicas는 어떻게 다른가?"
> A: 이것은 가장 빈번하게 혼동되는 개념 중 하나이다. Multi-AZ는 고가용성 (HA)을 위한 구조이며, 스탠바이 레플리카는 읽기 트래픽을 처리하지 않는다. Read Replica는 읽기 스케일링을 위한 구조이며, 비동기 레플리케이션으로 데이터를 복제하여 SELECT 쿼리를 분산한다. Multi-AZ는 자동 페일오버를 제공하지만, Read Replica는 수동으로 프라이머리로 승격시킬 필요가 있다. 양자는 병용 가능하며, 「Multi-AZ + Read Replicas」가 운영 환경의 권장 구성이다.

**현실 세계의 비유 (비IT 대상):**
> "Multi-AZ는 은행의 본점과 지점과 같은 것. 본점 (프라이머리)이 화재로 폐쇄되어도, 지점 (스탠바이)이 즉시 업무를 인계한다. 고객은 같은 전화번호 (DNS 엔드포인트)로 연락할 수 있고, 통장의 기록 (데이터)은 본점과 지점에서 항상 동기화되어 있다"

**Multi-AZ vs Read Replica 비교표:**

| 관점 | Multi-AZ | Read Replica |
|------|---------|-------------|
| **목적** | 고가용성 (HA) | 읽기 스케일링 |
| **레플리케이션 방식** | 동기 | 비동기 |
| **페일오버** | 자동 (60-120초) | 수동 승격 |
| **읽기 트래픽** | 스탠바이에서는 처리하지 않음 | 읽기 쿼리를 처리 |
| **엔드포인트** | 단일 DNS (변경 불필요) | 각 레플리카에 전용 엔드포인트 |
| **크로스 리전** | 불가 | 가능 |
| **레플리카 수** | 1 (스탠바이) | 최대 5 (RDS) / 15 (Aurora) |
| **데이터 손실 리스크** | 없음 (동기) | 있음 (비동기 래그) |
| **비용** | 스탠바이 인스턴스 과금 | 레플리카 인스턴스 과금 |

### RDS Read Replicas

**정의:** 프라이머리 DB 인스턴스로부터 비동기 레플리케이션으로 데이터를 복제하는 읽기 전용 레플리카. RDS에서는 최대 5개, Aurora에서는 최대 15개의 Read Replica를 생성 가능. 같은 리전, 크로스 리전, 나아가 크로스 계정에서의 생성이 가능하다.

**소크라테스식 심화:**
> Q: "Read Replica는 어떤 장면에서 사용하는가?"
> A: 웹 애플리케이션에서는 일반적으로 읽기 (SELECT)가 쓰기 (INSERT/UPDATE/DELETE)의 10배 이상 많다. Read Replica를 사용함으로써, 리포트 생성이나 애널리틱스 쿼리를 레플리카로 분배하여 프라이머리 DB의 부하를 경감할 수 있다. 예를 들어, EC 사이트에서 상품 검색 (읽기)은 Read Replica로, 주문 처리 (쓰기)는 프라이머리로 라우팅하는 구성이 전형적이다.
> Q: "비동기 레플리케이션의 단점은 무엇인가?"
> A: 비동기 레플리케이션에는 「레플리케이션 래그」가 존재한다. 프라이머리에 기록된 데이터가 레플리카에 반영되기까지 수초에서 수십 초의 타임 래그가 발생할 가능성이 있다. 즉, 사용자가 주문을 완료한 직후에 Read Replica에서 주문 이력을 읽으면, 그 주문이 표시되지 않을 수 있다 (최종적으로는 반영된다: Eventual Consistency). 강한 일관성이 필요한 읽기는 프라이머리로 향하는 설계가 필요하다.
> Q: "Read Replica를 스탠드얼론 프라이머리로 승격시키는 것은 어떤 장면인가?"
> A: (1) DR 시에 크로스 리전 Read Replica를 그 리전의 프라이머리로 승격시킨다. (2) 데이터베이스 마이그레이션 시에 Read Replica를 컷오버 대상으로 한다. 승격 후에는 레플리케이션이 절단되어, 독립적인 프라이머리 DB로서 동작한다. 승격 프로세스는 비가역적이라는 점에 주의.

**Read Replica 네트워크 비용:**
- 같은 리전 내의 레플리케이션: **무료**
- 크로스 리전 레플리케이션: **리전 간 데이터 전송 요금 발생**

### Amazon Aurora

**정의:** AWS가 개발한 MySQL/PostgreSQL 호환의 클라우드 네이티브 관계형 데이터베이스 엔진. 3개의 AZ에 걸친 6카피의 분산 스토리지 아키텍처에 의해, 표준 RDS와 비교하여 MySQL의 최대 5배, PostgreSQL의 최대 3배의 스루풋을 제공한다.

**소크라테스식 심화:**
> Q: "Aurora는 RDS와 어떻게 다른가? 왜 별도의 서비스로 존재하는가?"
> A: Aurora는 RDS의 프레임워크 위에서 동작하지만, 스토리지 레이어가 근본적으로 다르다. 표준 RDS는 EBS 기반의 스토리지를 사용하지만, Aurora는 독자적인 분산 스토리지 시스템을 채택하고 있다. 데이터는 3개의 AZ에 6카피 저장되며, 쓰기에는 6카피 중 4카피의 합의 (4/6 quorum), 읽기에는 3카피의 합의 (3/6 quorum)가 필요하다. 이 설계에 의해, 2개의 카피가 동시에 소실되어도 쓰기가, 3개가 소실되어도 읽기가 계속 가능하며, AZ 장애에 대한 내성이 격단히 높다.
> Q: "Aurora Serverless v2란 무엇인가?"
> A: Aurora Serverless v2는 데이터베이스의 용량을 워크로드에 따라 자동으로 스케일링하는 구성이다. ACU (Aurora Capacity Unit)라는 단위로 0.5~128 ACU의 범위에서 자동 스케일한다. 1 ACU는 약 2 GB의 메모리와 대응하는 CPU에 상당한다. 트래픽이 적은 야간에는 최소 ACU까지 축소되고, 피크 시에는 수초 만에 확대된다. 예측 불가능한 워크로드나 개발 환경의 비용 최적화에 최적이다.
> Q: "Aurora Global Database란 무엇인가?"
> A: Aurora Global Database는 복수의 AWS 리전에 걸친 데이터베이스 레플리케이션을 실현하는 기능이다. 프라이머리 리전에서 세컨더리 리전으로의 전형적인 레플리케이션 래그는 1초 미만이며, 리전 장애 시에는 1분 미만으로 세컨더리 리전을 프라이머리로 승격할 수 있다. 글로벌하게 전개하는 애플리케이션의 DR 전략과 저레이턴시 읽기에 사용된다.

**현실 세계의 비유 (비IT 대상):**
> "Aurora는 초고성능 금고실과 같은 것. 맡긴 서류 (데이터)는 자동으로 3개의 다른 건물 (AZ)의 6개의 금고 (카피)에 보관된다. 2개의 금고가 부서져도 서류는 꺼낼 수 있고, 3개가 부서져도 읽을 수 있다. 보통의 RDS가 1개의 금고에 서류를 보관하는 것에 비해, Aurora는 처음부터 분산 보관하는 설계이므로, 재해에 극히 강하다"

**RDS vs Aurora 비교표:**

| 관점 | RDS (표준) | Aurora |
|------|-----------|--------|
| **엔진** | MySQL, PostgreSQL, MariaDB, Oracle, SQL Server | MySQL 호환, PostgreSQL 호환만 |
| **스토리지** | EBS 기반 (gp3, io1, io2) | 독자 분산 스토리지 (3 AZ, 6카피) |
| **스토리지 용량** | 최대 64 TiB | 자동 확장 10 GB~128 TB |
| **Read Replicas** | 최대 5 | 최대 15 |
| **페일오버 시간** | 60-120초 | 30초 미만 |
| **레플리케이션 방식** | 비동기 (Read Replica) | 공유 스토리지 (레플리케이션 불필요) |
| **Serverless** | 없음 | Serverless v2 (0.5-128 ACU) |
| **Global Database** | 크로스 리전 Read Replica | 전용 Global Database (래그 < 1초) |
| **클로닝** | 스냅샷에서 복원 | Copy-on-Write (수분 만에 완료) |
| **Backtrack** | 없음 | 있음 (최대 72시간 되감기) |
| **비용** | 비교적 저비용 | RDS 대비 약 20% 증가, 성능 향상분으로 상쇄 |

**Aurora 클로닝 vs 스냅샷 복원:**
- **클로닝:** Copy-on-Write 프로토콜에 의해, 원본 데이터를 공유하는 형태로 클론을 생성한다. 데이터 사이즈에 관계없이 수분 만에 완료되며, 추가 스토리지는 변경된 페이지분만 소비한다. 개발·테스트 환경의 생성에 최적.
- **스냅샷 복원:** 스냅샷에서 새로운 클러스터를 생성한다. 데이터의 완전 복사가 필요하므로, 데이터 사이즈에 따라 시간이 걸린다. 다른 리전이나 계정으로의 이전에 사용.

### Amazon DynamoDB

**정의:** 풀매니지드의 키-밸류 & 문서 데이터베이스 서비스. 임의의 스케일에서 싱글 디짓 밀리초의 레이턴시를 제공한다. 파티션 키와 옵션의 정렬 키로 테이블 설계를 하며, 프로비전드 캐퍼시티 모드와 온디맨드 캐퍼시티 모드의 2가지 과금 모델에서 선택한다.

**소크라테스식 심화:**
> Q: "DynamoDB는 RDS/Aurora와 어떻게 다른가? 어떤 장면에서 선택하는가?"
> A: DynamoDB는 NoSQL 데이터베이스이며, RDS/Aurora의 관계형 모델 (테이블, 행, 열, JOIN)과는 근본적으로 다르다. DynamoDB에는 스키마리스의 아이템 (행)과 어트리뷰트 (열)가 있지만, JOIN이나 트랜잭션의 복잡한 결합은 지원하지 않는다 (2018년부터 심플한 트랜잭션은 대응). DynamoDB가 빛나는 장면은, (1) 예측 가능한 액세스 패턴, (2) 수평 스케일링이 필요, (3) 밀리초 수준의 레이턴시가 요구됨, (4) 서버리스 아키텍처와의 통합, 이라는 케이스이다. 반대로, 복잡한 쿼리, 다대다 관계, 애드혹 리포트 생성에는 RDS/Aurora가 적합하다.
> Q: "프로비전드 캐퍼시티와 온디맨드 캐퍼시티의 차이는?"
> A: 프로비전드는 「월정액 헬스장 회원권」과 같은 것. RCU (Read Capacity Unit)와 WCU (Write Capacity Unit)를 사전에 설정하고, 그 범위 내에서 스로틀링 없이 액세스할 수 있다. Auto Scaling과 병용하여 수요 변동에 추종시키는 것도 가능. 온디맨드는 「건별 결제 헬스장」과 같은 것. 캐퍼시티 플래닝 불필요로, 리퀘스트마다 과금된다. 트래픽이 예측 불가능한 워크로드나 신규 서비스의 런칭 시에 적합하다. 다만, 안정적인 트래픽에서는 프로비전드 쪽이 최대 약 70% 비용 절감 가능하다.

**현실 세계의 비유 (비IT 대상):**
> "DynamoDB는 거대한 서류 캐비닛과 같은 것. 각 서랍 (파티션)에는 라벨 (파티션 키)이 붙어 있고, 서랍 안의 파일은 탭 (정렬 키)으로 정리되어 있다. 라벨을 지정하면 순식간에 목적 파일에 도달할 수 있다. 다만, 라벨을 모르면 모든 서랍을 열어 찾아야 하며 (풀 스캔), 매우 시간이 걸린다. 설계의 핵심은 가장 많이 사용하는 검색 패턴에 맞추어 라벨 부착 방법을 결정하는 것이다"

**DynamoDB 캐퍼시티 모드 비교:**

| 관점 | 프로비전드 | 온디맨드 |
|------|---------|---------|
| **과금** | RCU/WCU 단위의 고정 + Auto Scaling | 리퀘스트 단위의 종량 |
| **캐퍼시티 플래닝** | 필요 | 불필요 |
| **비용 (안정 트래픽)** | 저렴 (최대 70% 절감) | 높음 |
| **비용 (불규칙 트래픽)** | 과잉 프로비저닝의 리스크 | 최적 |
| **스로틀링** | 캐퍼시티 초과 시 발생 | 사실상 없음 |
| **스케일링 속도** | Auto Scaling: 수분 | 즉시 |
| **리저브드 캐퍼시티** | 1년/3년 예약으로 추가 할인 | 없음 |
| **권장 케이스** | 예측 가능한 운영 워크로드 | 신규 서비스, 버스트성 워크로드 |

**DynamoDB의 주요 기능:**
- **DAX (DynamoDB Accelerator):** 인메모리 캐시 레이어. 레이턴시를 밀리초에서 마이크로초로 단축. API 호환으로 코드 변경 최소한.
- **Global Tables:** 멀티 리전에서의 양방향 레플리케이션. 액티브-액티브 구성. RPO/RTO = 약 0.
- **TTL (Time to Live):** 아이템의 유효 기한을 설정하여, 기한 만료 아이템을 자동 삭제. 세션 데이터나 로그에 최적.
- **DynamoDB Streams:** 테이블의 변경 (INSERT/UPDATE/DELETE)을 캡처하는 이벤트 스트림. Lambda 함수의 트리거로 사용.
- **Point-in-Time Recovery (PITR):** 과거 35일간의 임의의 시점에 테이블을 복원 가능.

### DynamoDB 설계 패턴

**정의:** DynamoDB의 설계는, 관계형 데이터베이스와는 근본적으로 다른 접근 방식을 필요로 한다. 액세스 패턴을 먼저 정의하고, 그에 최적화된 테이블 설계를 수행하는 「액세스 패턴 구동 설계」가 기본 원칙이다.

**소크라테스식 심화:**
> Q: "싱글 테이블 설계란 무엇인가? 왜 복수 테이블이 아닌가?"
> A: DynamoDB에서는 JOIN을 사용할 수 없으므로, 관계형 DB처럼 정규화하여 복수 테이블로 분할하면 애플리케이션 측에서 결합 로직을 구현할 필요가 있다. 싱글 테이블 설계에서는, 사용자, 주문, 상품 등의 다른 엔티티를 1개의 테이블에 「타입 식별자」를 사용하여 격납한다. 예를 들어, 파티션 키=「USER#123」, 정렬 키=「ORDER#456」와 같이 설계함으로써, 1개의 쿼리로 사용자와 그 주문을 동시에 취득할 수 있다. 다만, 싱글 테이블 설계는 복잡하며, 모든 케이스에서 필수는 아니다.
> Q: "GSI (Global Secondary Index)와 LSI (Local Secondary Index)의 차이는?"
> A: LSI는 베이스 테이블과 같은 파티션 키로 다른 정렬 키를 가지는 인덱스이며, 테이블 생성 시에만 정의 가능하다 (나중에 추가 불가). GSI는 완전히 다른 파티션 키와 정렬 키를 가지는 인덱스이며, 테이블 생성 후에도 추가·삭제 가능하다. GSI는 테이블과는 독립적인 캐퍼시티를 가지므로, 인덱스에의 쓰기가 별도로 WCU를 소비한다. LSI는 테이블의 캐퍼시티를 공유한다.

**DynamoDB 설계 테크닉:**
- **스파스 인덱스:** GSI의 어트리뷰트가 존재하는 아이템만 인덱스에 포함되는 성질을 이용하여, 특정 상태의 아이템만을 효율적으로 쿼리한다 (예: `status=ACTIVE`인 아이템만의 GSI).
- **라이트 샤딩:** 핫 파티션을 회피하기 위해, 파티션 키의 말미에 랜덤한 서픽스를 추가한다 (예: `ORDER#2026-02-11#1`, `ORDER#2026-02-11#2`). 읽기 시는 전 서픽스를 병렬 쿼리하여 결과를 머지한다.
- **핫 파티션 회피:** 특정 파티션 키에 액세스가 집중되면, 그 파티션이 병목이 된다. 키 설계의 궁리와 DAX 캐시의 활용으로 분산시킨다.

**GSI vs LSI 비교표:**

| 관점 | GSI (Global Secondary Index) | LSI (Local Secondary Index) |
|------|------|------|
| **파티션 키** | 베이스 테이블과 다른 키 선택 가능 | 베이스 테이블과 동일 |
| **정렬 키** | 임의의 어트리뷰트 | 임의의 어트리뷰트 |
| **생성 타이밍** | 언제든지 추가·삭제 가능 | 테이블 생성 시에만 |
| **캐퍼시티** | 독립된 RCU/WCU | 베이스 테이블과 공유 |
| **사이즈 제한** | 없음 | 파티션당 10 GB |
| **일관성** | Eventual Consistency만 | Strong Consistency 선택 가능 |
| **테이블당 상한** | 20 | 5 |

### RDS Performance Insights

**정의:** RDS 및 Aurora의 데이터베이스 퍼포먼스를 시각적으로 분석하기 위한 모니터링 기능. 톱 SQL 쿼리, 대기 이벤트, DB 부하 (DBLoad), 카운터 메트릭스를 제공하여, 퍼포먼스의 병목을 신속하게 특정할 수 있다.

**소크라테스식 심화:**
> Q: "Performance Insights로 무엇을 알 수 있는가?"
> A: Performance Insights의 핵심 지표는 「DB Load」이다. 이것은 데이터베이스의 액티브 세션 수의 시계열 데이터이며, vCPU 수의 임계치와 비교함으로써 CPU가 병목인지 아닌지를 판단할 수 있다. DB Load가 vCPU 수를 초과하고 있는 경우, 세션이 대기 상태에 있다. 대기 이벤트 (예: `io/table/sql/handler`, `lock/table/sql/handler`)를 분석함으로써, I/O 대기인지 락 대기인지를 특정하고, 적절한 대책 (인덱스 추가, 쿼리 최적화, 인스턴스 사이즈 변경)을 강구할 수 있다.
> Q: "보유 기간의 차이는?"
> A: 무료 티어에서는 7일간의 퍼포먼스 데이터를 보유한다. 유료 티어 (인스턴스별 추가 요금)에서는 최대 2년간의 데이터를 보유할 수 있으며, 장기적인 트렌드 분석이나 캐퍼시티 플래닝에 활용 가능하다.

### RDS Proxy

**정의:** RDS 및 Aurora 데이터베이스에의 접속을 풀링·관리하는 풀매니지드의 데이터베이스 프록시. 애플리케이션과 데이터베이스 사이에 배치되어, 접속 풀링, IAM 인증, 페일오버 시간의 단축을 제공한다.

**소크라테스식 심화:**
> Q: "RDS Proxy는 왜 필요한가?"
> A: 데이터베이스 접속은 「고속도로의 차선」과 같은 것이다. 각 접속은 메모리와 CPU 리소스를 소비한다. Lambda 함수와 같은 서버리스 애플리케이션에서는, 동시에 수백~수천의 리퀘스트가 발생하여, 각각이 데이터베이스 접속을 확립하려 한다. 이것은 데이터베이스의 접속 상한을 용이하게 초과시켜, `Too many connections` 에러를 일으킨다. RDS Proxy는 접속 풀을 관리하여, 다수의 애플리케이션 접속을 소수의 데이터베이스 접속에 매핑함으로써 이 문제를 해결한다.
> Q: "페일오버 시간의 단축이란 어느 정도인가?"
> A: RDS Proxy를 사용하지 않는 경우, Multi-AZ 페일오버에는 60~120초가 걸리며, 이 동안 애플리케이션의 접속은 타임아웃한다. RDS Proxy는 페일오버를 검지하면, 새로운 프라이머리에의 접속을 자동으로 확립하고, 기존의 클라이언트 접속을 리다이렉트한다. 이에 의해 애플리케이션 측의 다운타임이 대폭 단축된다 (최대 66% 단축).

**현실 세계의 비유 (비IT 대상):**
> "RDS Proxy는 대형 레스토랑의 프런트와 같은 것. 개별 고객 (애플리케이션 접속)이 직접 주방 (데이터베이스)에 들어가면 혼란이 생기지만, 프런트 (Proxy)가 좌석 (접속 풀)을 관리하여 효율적으로 고객을 안내한다. 주방이 다른 장소로 이전 (페일오버)해도, 프런트가 새로운 장소로의 안내를 자동으로 전환하므로, 고객은 알아차리지 못한다"

**RDS Proxy의 주요 기능:**

| 기능 | 설명 |
|------|------|
| **접속 풀링** | 다수의 애플리케이션 접속을 소수의 DB 접속에 매핑 |
| **IAM 인증** | 데이터베이스 인증을 IAM 역할/정책과 통합 |
| **Secrets Manager 통합** | DB 인증 정보를 Secrets Manager에서 자동 취득 |
| **페일오버 단축** | Multi-AZ 페일오버 시의 다운타임 최대 66% 단축 |
| **Multi-AZ** | Proxy 자체가 Multi-AZ로 고가용성 |
| **핀 고정 회피** | 세션 상태 관리의 최적화로 접속 재이용률을 향상 |

### 데이터베이스 마이그레이션 (AWS DMS / SCT)

**정의:** AWS Database Migration Service (DMS)는 데이터베이스의 마이그레이션을 지원하는 서비스이며, Schema Conversion Tool (SCT)은 이종 데이터베이스 간의 스키마 변환을 수행하는 도구이다. 소스 DB를 가동시킨 채로 최소 다운타임에서의 마이그레이션을 실현한다.

**소크라테스식 심화:**
> Q: "동종 마이그레이션과 이종 마이그레이션의 차이는?"
> A: 동종 마이그레이션 (Homogeneous Migration)은 같은 엔진 간의 마이그레이션 (예: 온프레미스 Oracle → RDS Oracle)이며, 스키마 변환은 불필요하다. DMS만으로 마이그레이션이 완료된다. 이종 마이그레이션 (Heterogeneous Migration)은 다른 엔진 간의 마이그레이션 (예: Oracle → Aurora PostgreSQL)이며, 먼저 SCT로 스키마 (테이블 정의, 스토어드 프로시저, 뷰)를 변환하고, 다음으로 DMS로 데이터를 마이그레이션한다.
> Q: "CDC (Change Data Capture)란 무엇인가?"
> A: CDC는 소스 데이터베이스에서 발생하는 변경 (INSERT/UPDATE/DELETE)을 실시간으로 포착하여, 타겟 데이터베이스에 지속적으로 레플리케이션하는 구조이다. 최초의 풀 로드 마이그레이션 후에 CDC를 활성화함으로써, 컷오버 (운영 전환)까지의 동안에도 소스의 변경이 타겟에 반영되어 계속된다. 최종적인 다운타임은 CDC 래그분 (통상 수초~수분)으로 축소된다.

**현실 세계의 비유 (비IT 대상):**
> "DMS는 이사 업체와 같은 것. 구 거처 (소스 DB)에서 신 거처 (타겟 DB)로 짐 (데이터)을 운반한다. 동종 마이그레이션은 같은 간살의 집으로의 이사 (가구가 그대로 들어간다). 이종 마이그레이션은 전혀 다른 간살의 집으로의 이사 (SCT로 가구의 사이즈를 조정한 후 운반한다). CDC는 이사 중에도 구 거처에서 매일 늘어나는 짐을 실시간으로 운반 계속하는 서비스이다"

**DMS 마이그레이션 패턴:**

| 마이그레이션 타입 | 소스 → 타겟 | SCT 필요? | 예 |
|----------------|-----------|---------|-----|
| 동종 | 같은 엔진 | 불필요 | MySQL → RDS MySQL |
| 이종 | 다른 엔진 | 필요 | Oracle → Aurora PostgreSQL |
| 통합 | 복수 소스 → 1 타겟 | 경우에 따라 | 복수 MySQL → Aurora MySQL |
| 레플리케이션 | AWS ↔ AWS | 불필요 | RDS → Aurora (지속적 레플리케이션) |

### 백업 & 복구

**정의:** RDS/Aurora의 백업은, 자동 백업 (Automated Backups), 수동 스냅샷 (Manual Snapshots), 포인트 인 타임 리커버리 (PITR)의 3가지 구조로 구성된다. Aurora에는 추가로 백트랙 (Backtrack) 기능이 있다.

**소크라테스식 심화:**
> Q: "자동 백업과 스냅샷의 차이는 무엇인가?"
> A: 자동 백업은 RDS가 매일 자동으로 취득하는 백업이며, 보유 기간은 0~35일 (기본값 7일, 0으로 비활성화). 보유 기간 내의 임의의 시점에 데이터베이스를 복원할 수 있다 (PITR). 5분마다의 트랜잭션 로그도 자동 저장된다. 수동 스냅샷은 사용자가 명시적으로 취득하는 백업이며, 보유 기한이 없다 (삭제할 때까지 영속). 자동 백업의 보유 기간을 초과하여 보유하고 싶은 데이터나, 메이저 업그레이드 전의 백업에 사용한다.
> Q: "Aurora Backtrack이란 무엇인가? PITR과 어떻게 다른가?"
> A: PITR은 새로운 데이터베이스 인스턴스를 생성하여 복원하므로, 복원에 시간이 걸리고, 엔드포인트도 바뀐다. Aurora Backtrack은 같은 클러스터 내에서 시간을 되감는다 (최대 72시간). 새로운 인스턴스를 생성하지 않으므로 고속이며, 엔드포인트도 바뀌지 않는다. 다만 Backtrack은 MySQL만 대응이며, 크로스 리전 레플리케이션이 유효한 클러스터에서는 사용할 수 없다.
> Q: "크로스 리전 스냅샷 복사는 어떤 장면에서 사용하는가?"
> A: RDS의 자동 백업은 프라이머리 리전에만 저장된다. 리전 장애에 대비한 DR 전략으로서, 스냅샷을 다른 리전에 복사해 둘 필요가 있다. 수동 스냅샷의 크로스 리전 복사는 수동 또는 Lambda/EventBridge로 자동화할 수 있다. Aurora의 경우는 Global Database가 권장 DR 솔루션이다.

**백업 비교표:**

| 백업 방식 | 보유 기간 | 복원 대상 | 복원 시간 | 대상 |
|---------|---------|---------|---------|------|
| **자동 백업** | 0~35일 | 새로운 DB 인스턴스 | 데이터 사이즈 의존 | RDS, Aurora |
| **수동 스냅샷** | 무기한 | 새로운 DB 인스턴스 | 데이터 사이즈 의존 | RDS, Aurora |
| **PITR** | 자동 백업 보유 기간 내 | 새로운 DB 인스턴스 | 데이터 사이즈 의존 | RDS, Aurora |
| **Aurora Backtrack** | 최대 72시간 | 같은 클러스터 (되감기) | 수분 | Aurora (MySQL)만 |
| **크로스 리전 복사** | 무기한 | 다른 리전의 DB 인스턴스 | 데이터 사이즈 의존 | RDS, Aurora |

## 아키텍처 패턴

### 패턴1: Multi-AZ RDS + Read Replicas (읽기 부하 분산)

```
                        ┌────────────────────────────┐
                        │    Application Layer        │
                        │  ┌──────────┐ ┌──────────┐ │
                        │  │ Write Ops │ │ Read Ops │ │
                        │  └────┬─────┘ └────┬─────┘ │
                        └───────┼─────────────┼───────┘
                                │             │
                   ┌────────────▼──┐    ┌─────▼──────────────┐
                   │  RDS Primary   │    │  Read Replica(s)    │
                   │  (Multi-AZ)    │───→│  AZ-a, AZ-b, AZ-c  │
                   │  AZ-a          │    │  비동기 레플리케이션  │
                   │    ↕ 동기      │    └─────────────────────┘
                   │  Standby       │
                   │  AZ-b          │
                   └────────────────┘
```

쓰기는 프라이머리, 읽기는 Read Replica에 분산. Multi-AZ로 고가용성을 확보하면서, Read Replica로 스케일 아웃. 전형적인 웹 애플리케이션의 권장 구성이다.

### 패턴2: Aurora Global Database (글로벌 DR)

```
Primary Region (ap-northeast-1)         Secondary Region (us-west-2)
┌─────────────────────────────┐    ┌─────────────────────────────┐
│  Aurora Writer Instance      │    │  Aurora Reader Instance(s)   │
│  + Reader Instances (15)     │───→│  (로컬 읽기용)              │
│                              │ <1s│                              │
│  공유 스토리지 (6카피)        │ lag│  공유 스토리지 (6카피)        │
│  3 AZ × 2카피                │    │  3 AZ × 2카피                │
└─────────────────────────────┘    └─────────────────────────────┘
         ↓ 리전 장애 시                       ↓
  자동 검출 + 수동/자동 승격 (<1분)     → 새로운 프라이머리로 가동
```

프라이머리 리전 장애 시 1분 미만으로 세컨더리를 프라이머리로 승격. 레플리케이션 래그는 통상 1초 미만. 글로벌 전개의 애플리케이션에서는 세컨더리 리전의 Reader로 로컬 읽기도 가능.

### 패턴3: DynamoDB + DAX (마이크로초 레이턴시)

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Application  │────→│  DAX Cluster  │────→│  DynamoDB     │
│  (Lambda 등)  │     │  (In-Memory)  │     │  Table        │
│               │     │  마이크로초    │     │  밀리초       │
└──────────────┘     └──────────────┘     └──────────────┘
                           │                     │
                      캐시 히트              캐시 미스
                      → 마이크로초 응답      → 밀리초 응답
                                                → 결과를 DAX에 캐시
```

DAX는 DynamoDB API와 호환의 인메모리 캐시. 코드 변경 최소한으로 레이턴시를 밀리초에서 마이크로초로 단축. 리드 헤비 워크로드에서 DynamoDB의 RCU 소비를 대폭 절감.

### 패턴4: Lambda + RDS Proxy (서버리스 DB 접속)

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  API Gateway  │────→│  Lambda       │────→│  RDS Proxy    │
│               │     │  (수백 동시)   │     │  접속 풀링    │
└──────────────┘     └──────────────┘     │              │
                                          └──────┬───────┘
                                                 │
                                     ┌───────────▼────────────┐
                                     │  RDS/Aurora             │
                                     │  (Multi-AZ)             │
                                     │  최대 접속 수에 수렴     │
                                     └─────────────────────────┘
```

Lambda 함수의 동시 실행 수가 급증해도, RDS Proxy가 접속 풀을 관리하여 데이터베이스의 접속 수를 적절한 범위에 유지. IAM 인증과 Secrets Manager 통합으로 시큐어한 접속 관리를 실현.

### 패턴5: DMS에 의한 데이터베이스 마이그레이션 (최소 다운타임)

```
Phase 1: 풀 로드
┌──────────────┐                      ┌──────────────┐
│  Source DB    │───── DMS ───────────→│  Target DB    │
│  (On-Prem)   │  풀 로드             │  (RDS/Aurora) │
└──────────────┘                      └──────────────┘

Phase 2: CDC (지속적 레플리케이션)
┌──────────────┐                      ┌──────────────┐
│  Source DB    │───── DMS (CDC) ─────→│  Target DB    │
│  가동 중      │  변경만 전송         │  차분 동기 중  │
└──────────────┘                      └──────────────┘

Phase 3: 컷오버
┌──────────────┐                      ┌──────────────┐
│  Source DB    │     CDC 래그≒0       │  Target DB    │
│  앱 정지      │  ← 최종 동기 →       │  앱 전환      │
└──────────────┘                      └──────────────┘
```

풀 로드 → CDC → 컷오버의 3페이즈로 마이그레이션. 소스 DB를 가동시킨 채로 마이그레이션을 진행하여, 최종 컷오버 시의 다운타임을 CDC 래그분 (수초~수분)으로 최소화한다.

## SAA 시험 포인트

| 토픽 | 출제 포인트 | 키워드 |
|------|-----------|--------|
| **RDS Multi-AZ vs Read Replicas** | Multi-AZ는 고가용성 (동기 레플리케이션), Read Replica는 읽기 스케일링 (비동기 레플리케이션). 양자 병용 가능 | 동기 vs 비동기, 자동 페일오버 |
| **Aurora 스토리지** | 자동 확장 10 GB~128 TB. 3 AZ × 2카피 = 6카피. 쓰기 4/6 합의, 읽기 3/6 합의 | 자동 확장, 6카피, 쿼럼 |
| **DynamoDB 프로비전드 vs 온디맨드** | 안정 트래픽 → 프로비전드 + Auto Scaling (최대 70% 저렴). 불안정 → 온디맨드 | RCU/WCU, Auto Scaling |
| **RDS 자동 백업 보유 기간** | 0~35일 (0으로 비활성화). 기본값 7일. 보유 기간 내에서 PITR 가능 (5분 세분도) | 35일 상한, PITR, 5분 세분도 |
| **Aurora 페일오버 시간** | 30초 미만. RDS 표준은 60-120초. RDS Proxy로 추가 단축 가능 | 30초 미만, DNS 전환 |
| **DynamoDB GSI vs LSI** | GSI는 나중에 추가 가능, 독립 캐퍼시티, Eventual Consistency. LSI는 테이블 생성 시에만, Strong Consistency 대응, 파티션 10 GB 제한 | GSI: 유연, LSI: 생성 시에만 |
| **RDS Proxy** | Lambda + RDS의 접속 문제를 해결. 접속 풀링, IAM 인증, 페일오버 단축. VPC 내에 배치 | 접속 풀링, Lambda 통합 |
| **Aurora Serverless v2 ACU** | 0.5~128 ACU. 수초 만에 스케일. 1 ACU ≈ 2 GB 메모리. v1은 0→기동에 30초 걸리지만 v2는 즉시 | 0.5-128 ACU, 즉시 스케일 |
| **DynamoDB DAX vs ElastiCache** | DAX는 DynamoDB 전용, API 호환으로 코드 변경 최소한. ElastiCache는 범용 캐시 (Redis/Memcached), 애플리케이션 측에서 캐시 로직의 구현이 필요 | DAX: DynamoDB 전용, ElastiCache: 범용 |
| **크로스 리전 Read Replica** | RDS: 크로스 리전 RR 생성 가능 (리전 간 전송 요금 발생). Aurora: Global Database 권장 (래그 < 1초) | CRR RR, Global Database |
| **Aurora 클로닝 vs 스냅샷** | 클로닝: Copy-on-Write, 수분 만에 완료, 스토리지 공유. 스냅샷 복원: 완전 복사, 시간 소요 | Copy-on-Write, 테스트 환경 |
| **DynamoDB Streams vs Kinesis Data Streams** | DynamoDB Streams: 24시간 보유, Lambda 통합, 테이블 고유. Kinesis Data Streams for DynamoDB: 1년 보유, 복수 컨슈머, 보다 유연한 스트림 처리 | 24h vs 1년, 보유 기간 |
| **DMS CDC** | 풀 로드 + CDC로 최소 다운타임 마이그레이션. SCT는 이종 마이그레이션에서 필요 | 풀 로드, CDC, SCT |
| **Aurora Backtrack** | 같은 클러스터 내에서 최대 72시간 되감기. MySQL 호환만. 새 인스턴스 불필요로 엔드포인트 불변 | 72시간, 되감기, MySQL |
| **DynamoDB Global Tables** | 멀티 리전의 액티브-액티브. 전 리전에서 읽기·쓰기 가능. RPO/RTO ≈ 0 | 액티브-액티브, 멀티 리전 |

## RDS vs Aurora vs DynamoDB 종합 비교

| 관점 | RDS | Aurora | DynamoDB |
|------|-----|--------|----------|
| **데이터 모델** | 관계형 (SQL) | 관계형 (SQL) | 키-밸류 / 문서 (NoSQL) |
| **엔진** | MySQL, PostgreSQL, MariaDB, Oracle, SQL Server | MySQL 호환, PostgreSQL 호환 | 독자 (매니지드) |
| **스케일링** | 수직 (인스턴스 사이즈 변경) | 수직 + Read Replica Auto Scaling | 수평 (자동 파티셔닝) |
| **최대 스토리지** | 64 TiB | 128 TB (자동 확장) | 사실상 무제한 |
| **레이턴시** | 밀리초 | 밀리초 | 밀리초 (DAX로 마이크로초) |
| **가용성** | Multi-AZ (60-120초 페일오버) | Multi-AZ (30초 미만) | 99.999% SLA (Global Tables) |
| **백업** | 자동 + 스냅샷 + PITR | 자동 + 스냅샷 + PITR + Backtrack | 온디맨드 + PITR + AWS Backup |
| **Serverless** | 없음 | Serverless v2 | 완전 서버리스 |
| **글로벌** | 크로스 리전 RR | Global Database | Global Tables |
| **비용** | 가장 저비용 | RDS 대비 약 20% 증가 | 스루풋 의존 |
| **권장 케이스** | 표준 OLTP, 레거시 앱 마이그레이션 | 고성능·고가용성 OLTP | 대규모 키-밸류, 서버리스 |

## Well-Architected 체크리스트

### Reliability (신뢰성)
- [ ] RDS/Aurora에서 Multi-AZ가 활성화되어 있는가
- [ ] 자동 백업의 보유 기간이 적절하게 설정되어 있는가 (권장: 7일 이상)
- [ ] 크리티컬한 데이터베이스에 크로스 리전 백업 또는 Global Database가 설정되어 있는가
- [ ] RDS Proxy를 사용하여 페일오버 시간을 단축하고 있는가 (특히 서버리스 아키텍처)
- [ ] DynamoDB의 Point-in-Time Recovery (PITR)가 활성화되어 있는가
- [ ] 정기적인 복원 테스트가 실시되고 있는가 (백업의 정합성 검증)
- [ ] Aurora Backtrack이 활성화되어 있는가 (MySQL 호환의 경우, 오퍼레이션 에러의 신속한 복구)

### Performance Efficiency (퍼포먼스 효율)
- [ ] RDS Performance Insights가 활성화되어, 톱 SQL과 Wait Events를 감시하고 있는가
- [ ] Read Replica로 읽기 워크로드를 분산하고 있는가
- [ ] DynamoDB의 GSI/LSI가 액세스 패턴에 최적화되어 있는가 (불필요한 스캔의 배제)
- [ ] DAX 또는 ElastiCache로 핫 데이터의 캐시를 구현하고 있는가
- [ ] Aurora Serverless v2로 워크로드에 따른 자동 스케일링을 활용하고 있는가
- [ ] RDS의 인스턴스 클래스와 스토리지 타입이 워크로드 요건에 부합하고 있는가

### Cost Optimization (비용 최적화)
