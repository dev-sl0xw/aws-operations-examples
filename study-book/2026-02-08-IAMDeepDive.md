# セクション02: IAM深堀り (IAM Deep Dive)
> Well-Architected Pillar: Security
> Day: 1 | 難易度: 中級

## 概要

AWS Identity and Access Management (IAM) は、AWSリソースへのアクセスを安全に制御するサービスである。「誰が」「何に」「どのような操作を」「どのような条件で」行えるかを定義する、AWSセキュリティの根幹を成すサービスだ。全てのAWS APIコールはIAMによって認証・認可されるため、IAMの理解なくしてAWSの運用は不可能である。

IAMのポリシー評価は複数のポリシータイプ(アイデンティティベース、リソースベース、パーミッションバウンダリー、SCP、セッションポリシー)を組み合わせた複雑なロジックに基づく。これらが適切に構成されていなければ、セキュリティホールや権限の過剰付与が発生する。特にマルチアカウント環境では、SCPとIAMポリシーの相互作用を正確に理解する必要がある。

また、外部IDプロバイダーとの連携(フェデレーション)は、現代のクラウド運用において不可欠である。SAML 2.0によるエンタープライズ連携、OIDCによるWebアプリケーション連携、GitHub ActionsからのCI/CDアクセスなど、JWTとSTS一時認証情報の仕組みを深く理解することが求められる。

## キーコンセプト

### IAMポリシー評価ロジック

**定義:** AWSがAPIリクエストを受信した際に、アクセスを許可するか拒否するかを決定する評価アルゴリズム。基本原則は「明示的Deny > 明示的Allow > 暗黙的Deny」である。

**評価フロー:**

```
リクエスト受信
  ↓
1. 明示的Denyが存在するか? → YES → アクセス拒否 (終了)
  ↓ NO
2. SCPで許可されているか? → NO → アクセス拒否 (終了)
  ↓ YES
3. リソースベースポリシーで許可? → YES → アクセス許可 (終了) ※同一アカウント内
  ↓ NO
4. アイデンティティベースポリシーで許可? → NO → アクセス拒否 (終了)
  ↓ YES
5. パーミッションバウンダリーで許可? → NO → アクセス拒否 (終了)
  ↓ YES
6. セッションポリシーで許可? → NO → アクセス拒否 (終了)
  ↓ YES
7. アクセス許可
```

**ソクラテス式 深堀り:**
> Q: 「なぜ明示的Denyが最も強いのか?」
> A: セキュリティの観点から「禁止は常に許可に勝つ」のが原則である。例えば、あるユーザーにS3の全アクセスを許可するポリシーと、特定バケットへのアクセスを拒否するポリシーが両方適用されている場合、拒否が優先される。これにより、管理者は「何があっても絶対にやらせたくない操作」を確実にブロックできる。
> Q: 「では、明示的Denyがないとどうなるか?」
> A: 複数のポリシーが重なる環境では、意図しないアクセス許可が生じるリスクがある。例えば、チームAのポリシーでS3全バケットへのアクセスを許可し、チームBのポリシーでも同じ許可がある場合、特定の機密バケットだけをブロックする手段がなくなる。明示的Denyはこの「最後の砦」として機能する。

**現実世界のたとえ (非IT向け):**
> 「裁判所のようなもの。明示的な有罪判決(Deny)が最も強く、無罪判決(Allow)より優先されます。判決がなければ(暗黙的)、推定有罪(デフォルトDeny)です。たとえ10人の証人が無罪を主張しても、1つの明示的な有罪判決があれば有罪です」

### ポリシータイプの全体像

**定義:** IAMには複数のポリシータイプが存在し、それぞれ異なるレベルで権限を制御する。

| ポリシータイプ | アタッチ先 | 主な用途 |
|--------------|-----------|---------|
| **アイデンティティベース** | ユーザー、グループ、ロール | 「この人に何を許可するか」 |
| **リソースベース** | S3バケット、SQSキュー、Lambda等 | 「このリソースに誰がアクセスできるか」 |
| **パーミッションバウンダリー** | ユーザー、ロール | 「この人が持てる権限の上限」 |
| **SCP** | OU、アカウント | 「このアカウント全体の権限の上限」 |
| **セッションポリシー** | STS AssumeRole時 | 「このセッションだけの追加制限」 |

**パーミッションバウンダリーの仕組み:**
パーミッションバウンダリーは、ユーザーやロールが持てる最大権限を定義する。実効権限はアイデンティティベースポリシーとパーミッションバウンダリーの**交差部分**のみとなる。

```
実効権限 = アイデンティティベースポリシー ∩ パーミッションバウンダリー
```

例えば、アイデンティティベースポリシーで全AWSサービスへのアクセスを許可しても、パーミッションバウンダリーがS3とDynamoDBのみを許可していれば、実効権限はS3とDynamoDBだけになる。

### JWT (JSON Web Token)

**定義:** JSONオブジェクトとしてエンコードされた、安全にクレーム(主張)を伝達するためのオープン標準 (RFC 7519)。ヘッダー、ペイロード、署名の3つの部分からなり、Base64URLでエンコードされてドット区切りで連結される。

**JWTの構造:**

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.    ← ヘッダー (Header)
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6Ikpv  ← ペイロード (Payload)
aG4gRG9lIiwiYWRtaW4iOnRydWV9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← 署名 (Signature)
```

| 部分 | 内容 | 例 |
|------|------|-----|
| **Header** | アルゴリズム情報、トークンタイプ | `{"alg": "RS256", "typ": "JWT"}` |
| **Payload** | クレーム (ユーザー情報、権限、有効期限等) | `{"sub": "user123", "iss": "google.com", "exp": 1700000000}` |
| **Signature** | Header + Payload を秘密鍵で署名したもの | HMAC-SHA256 または RSA署名 |

**ソクラテス式 深堀り:**
> Q: 「JWTとは何か?なぜ認証に使われるのか?」
> A: JWTは「この人は誰で、何ができるか」という情報を改ざん不可能な形でパッケージングしたトークンである。従来のセッション方式では、サーバーがセッションIDとユーザー情報の対応表をメモリやDBに保持する必要があった(ステートフル)。JWTを使えば、トークン自体にユーザー情報が含まれているため、サーバーは状態を保持する必要がない(ステートレス)。これはマイクロサービスやサーバーレスアーキテクチャで特に重要だ。
> Q: 「JWTのペイロードは誰でも読めるのに、なぜ安全なのか?」
> A: JWTのペイロードはBase64エンコードされているだけで暗号化されていないため、誰でも読める。しかし、署名 (Signature) があるため改ざんは検出できる。ペイロードを1文字でも変更すれば署名が一致しなくなり、トークンは無効と判断される。つまりJWTは「機密性」ではなく「完全性」を保証する仕組みである。機密情報をペイロードに含めるべきではない(必要なら JWE: JSON Web Encryption を使う)。

**現実世界のたとえ (非IT向け):**
> 「雇用主からの封印された改ざん防止封筒のようなもの。封筒の表面に『この人はJohn、エンジニア、部署X所属』と書いてある(ペイロード)。誰でも封筒を見て読める(base64デコード)が、雇用主の印鑑(電子署名)だけが内容の真正性を証明します。印鑑を偽造することはできません。もし誰かが『部署X所属』を『部署Y所属』に書き換えたら、印鑑が合わなくなり偽造がバレます」

### OIDC (OpenID Connect)

**定義:** OAuth 2.0プロトコルの上に構築された認証層。ユーザーの身元確認(認証)を標準化し、IDトークン(JWT形式)を発行する。OAuth 2.0が「認可」(何ができるか)のみを扱うのに対し、OIDCは「認証」(誰であるか)を追加する。

**OIDCのフロー (AWSとの連携):**

```
1. ユーザー → IDプロバイダー (Google等) にログイン
2. IDプロバイダー → IDトークン (JWT) を発行
3. ユーザー → AWSのSTS AssumeRoleWithWebIdentity にIDトークンを提示
4. STS → IDトークンを検証 (IDプロバイダーの公開鍵で署名確認)
5. STS → 一時的なAWS認証情報 (Access Key, Secret Key, Session Token) を発行
6. ユーザー → 一時認証情報でAWSリソースにアクセス
```

**ソクラテス式 深堀り:**
> Q: 「OIDCとは何か?OAuth 2.0との違いは?」
> A: OAuth 2.0は「このアプリにXさんのGoogle Driveの読み取りを許可する」という認可のプロトコルだが、「Xさんは本当にXさんか」という認証は定義していない。OIDCはOAuth 2.0のフローの中にIDトークン(JWT)を追加し、ユーザーの身元情報を標準的な方法で取得できるようにした。AWSでは、このIDトークンをSTSに提示することで、外部IDプロバイダーのユーザーにAWSの一時認証情報を発行する。
> Q: 「なぜAWSアカウントごとにユーザーを作らないのか?」
> A: 企業が10個のAWSアカウントと500人の従業員を抱える場合、各アカウントにIAMユーザーを作ると5000個のユーザー管理が必要になる。パスワードポリシー、MFA、退職時の削除を5000個分管理するのは非現実的だ。フェデレーションを使えば、既存のID管理システム(Active Directory、Okta等)の一元管理で済む。

**現実世界のたとえ (非IT向け):**
> 「ホテルで政府発行のIDを見せるようなもの。ホテル(AWS)は政府(Google, GitHub等のIDプロバイダー)を既に信頼しています。ホテル専用の新しいIDを作る必要はありません。パスポートを見せるだけでチェックインでき、ルームキー(一時認証情報)がもらえます。パスポートの有効性はホテルが政府のデータベースに問い合わせて確認します」

### STS (Security Token Service)

**定義:** AWS STSは一時的なセキュリティ認証情報を発行するサービス。一時認証情報はAccess Key ID、Secret Access Key、Session Tokenの3つ組で構成され、指定した有効期限が過ぎると自動的に無効化される。

**主要なSTSアクション:**

| アクション | 用途 | 最大有効期限 |
|-----------|------|-------------|
| `AssumeRole` | 別のロールの権限を取得 | 最大12時間 (デフォルト1時間) |
| `AssumeRoleWithSAML` | SAML 2.0フェデレーション | 最大12時間 |
| `AssumeRoleWithWebIdentity` | OIDC/Web IDフェデレーション | 最大12時間 |
| `GetSessionToken` | MFA認証付き一時認証情報 | 最大36時間 |
| `GetFederationToken` | フェデレーションユーザー用 | 最大36時間 |

**ロールの連鎖 (Role Chaining):**

```
ユーザーA → AssumeRole(RoleB) → AssumeRole(RoleC) → AWSリソースアクセス
```

ロールチェインの場合、セッションの最大有効期限は**1時間**に制限される(個別のロールの最大セッション期間設定に関わらず)。

**ソクラテス式 深堀り:**
> Q: 「なぜ永続的なアクセスキーではなく一時認証情報を使うべきなのか?」
> A: 永続的なアクセスキーは漏洩した場合、手動でローテーションするまで無制限にアクセス可能である。GitHubに誤ってコミットされたアクセスキーが数分以内にボットに悪用されるケースは頻繁に報告されている。一時認証情報は有効期限が過ぎれば自動的に無効化されるため、漏洩時のリスクウィンドウが限定される。
> Q: 「ロールの連鎖で有効期限が1時間に制限されるのはなぜか?」
> A: セキュリティ上の理由である。ロールの連鎖は権限のエスカレーションパスとなりうるため、各リンクでの有効期限を短くすることでリスクを限定している。

**現実世界のたとえ (非IT向け):**
> 「オフィスビルの一時的な訪問者バッジ。名前とアクセスレベルが印刷され、午後5時に失効します。常設の社員証(永続的な認証情報)と違い、紛失しても時間が経てば使えなくなります。さらに、訪問者バッジは受付(STS)でしか発行されず、コピーはできません」

### 最小権限の原則 (Principle of Least Privilege)

**定義:** ユーザーやサービスに対して、業務遂行に必要最小限の権限のみを付与する原則。過剰な権限はセキュリティリスクの増大と監査の複雑化を招く。

**実装アプローチ:**

1. **初期:** 権限なしで開始し、必要に応じて追加する
2. **分析:** IAM Access Analyzerを使用して、CloudTrailのAPIコールログから実際に使用された権限を分析し、最小権限ポリシーを自動生成する
3. **制限:** パーミッションバウンダリーで権限の上限を設定する
4. **監視:** IAM Access Analyzerの外部アクセス分析で、意図しない外部共有を検出する

**IAM Access Analyzer の機能:**

| 機能 | 説明 |
|------|------|
| **外部アクセス分析** | S3バケット、IAMロール、KMSキー等が外部アカウントからアクセス可能かチェック |
| **未使用アクセス分析** | 90日以上使用されていない権限を検出 |
| **ポリシー生成** | CloudTrailの過去のAPIアクティビティに基づいて最小権限ポリシーを自動生成 |
| **ポリシー検証** | ポリシーの文法エラーやベストプラクティス違反をチェック |

**ソクラテス式 深堀り:**
> Q: 「なぜ最小権限が重要なのか?AdministratorAccessで全員に管理者権限を与えれば楽ではないか?」
> A: 短期的には楽だが、(1) 誤操作リスク: 開発者が本番データベースを誤って削除できてしまう、(2) 侵害時の被害拡大: 1つのアカウントが侵害されると全リソースにアクセス可能、(3) コンプライアンス違反: PCI DSS、SOC2等の認証取得が不可能になる。
> Q: 「しかし、最小権限の実装は煩雑ではないか?」
> A: IAM Access Analyzerがこの問題を大幅に緩和する。まず広めの権限を付与して運用し、90日後にCloudTrailの実際のAPIコールログから最小権限ポリシーを自動生成できる。完璧を最初から目指すのではなく、段階的に絞り込むアプローチが現実的だ。

**現実世界のたとえ (非IT向け):**
> 「ホテルのメイドに、その日の清掃担当の部屋だけ開くキーを渡すこと。建物全体のマスターキーではありません。万が一キーを落としても被害は最小限です。そして毎日キーの割り当てを見直し(IAM Access Analyzer)、使っていない部屋のキーは回収します」

### クロスアカウントアクセス

**定義:** あるAWSアカウントのIAMプリンシパルが、別のAWSアカウントのリソースにアクセスするパターン。主にIAMロールの信頼ポリシー(リソースベースポリシー)を使用して実現する。

**パターン1: ロールベースのクロスアカウントアクセス**

```
アカウントA (信頼される側)              アカウントB (信頼する側)
┌─────────────────────┐              ┌─────────────────────┐
│  IAM Role:          │              │  IAMユーザー/ロール   │
│  CrossAccountRole   │ ←AssumeRole─ │  (arn:aws:iam::B:...) │
│                     │              │                     │
│  Trust Policy:      │              │  IAM Policy:        │
│  "Principal":       │              │  sts:AssumeRole on  │
│  {"AWS": "arn:..B"} │              │  arn:..A:role/Cross  │
└─────────────────────┘              └─────────────────────┘
```

**パターン2: リソースベースポリシーによるクロスアカウントアクセス**

S3バケットポリシーなどリソースベースポリシーを直接設定する方法。この場合、アカウントBのユーザーはロールを引き受ける(AssumeRole)必要がなく、自身の認証情報のまま直接アクセスできる。

**重要な違い:**
- ロールベース: アクセス元は自身の権限を一時的に放棄し、ロールの権限に切り替わる
- リソースベース: アクセス元は自身の権限を保持したまま、追加でリソースにアクセスできる

### Identity Federation (SAML 2.0)

**定義:** SAML (Security Assertion Markup Language) 2.0は、エンタープライズ環境で広く使われる認証連携標準。Active Directory Federation Services (ADFS) やOkta等のIDプロバイダーとAWSを連携し、企業の既存認証基盤でAWSにログインできるようにする。

**SAMLフロー:**

```
1. ユーザー → 企業のIDプロバイダー (ADFS等) にログイン
2. IDプロバイダー → SAMLアサーション (XML) を発行
3. ユーザー → AWS Sign-In エンドポイントにSAMLアサーションをPOST
4. AWS STS → SAMLアサーションを検証
5. AWS STS → 一時認証情報を発行
6. ユーザー → AWSマネジメントコンソールにリダイレクト (または API アクセス)
```

## アーキテクチャパターン

### パターン1: 集中アクセス管理 (Identity Center)

```
AWS IAM Identity Center (旧 SSO)
  ├── 外部IDプロバイダー (Okta, Azure AD等) と連携
  ├── Permission Sets (権限セット) を定義
  └── アカウント × 権限セット の組み合わせでアクセス管理

ユーザー → SSO ポータル → アカウント選択 → ロール選択 → AWSコンソール/CLI
```

### パターン2: 階層的権限制御

```
SCP (組織レベルの上限)
  ∩
パーミッションバウンダリー (ユーザー/ロールレベルの上限)
  ∩
アイデンティティベースポリシー (実際に付与する権限)
  =
実効権限
```

各レイヤーは前のレイヤーの範囲内でのみ権限を付与できる。SCPで禁止された操作は、どれだけIAMポリシーで許可しても実行できない。

### パターン3: CI/CDパイプラインのOIDC連携

```
GitHub Actions
  ↓ (OIDCトークン)
AWS STS AssumeRoleWithWebIdentity
  ↓ (一時認証情報)
AWS リソースへのデプロイ
```

GitHub Actionsのワークフローでは、永続的なアクセスキーをシークレットに保存する代わりに、OIDCプロバイダーとしてGitHubを信頼し、ワークフロー実行時に一時認証情報を取得する。これにより、認証情報の漏洩リスクがゼロになる。

## SAA試験のポイント

- **ポリシー評価順序:** 明示的Deny > SCP > リソースベースポリシー > アイデンティティベースポリシー > パーミッションバウンダリー > セッションポリシー > 暗黙的Deny
- **リソースベースポリシーの特殊性:** 同一アカウント内では、リソースベースポリシーのAllowだけでアクセスが許可される(アイデンティティベースポリシーが不要)。クロスアカウントでは両方必要。
- **パーミッションバウンダリーはアクセスを付与しない。** 上限を設定するだけ。実際のアクセスにはアイデンティティベースポリシーが必要。
- **ロールの連鎖(Role Chaining)ではセッション有効期限が最大1時間** に制限される。
- **IAM Access Analyzerのポリシー生成** はCloudTrailのログに基づくため、CloudTrailが有効でなければ機能しない。
- **SAML 2.0フェデレーション** はエンタープライズ向け (ADFS, Okta)、**Web Identity / OIDC** はモバイルアプリやWebアプリ向け (Google, Facebook, Amazon)。
- **外部ID (ExternalId):** サードパーティにクロスアカウントアクセスを許可する際、「混乱した代理 (Confused Deputy)」問題を防ぐために使用する条件キー。
- **MFA条件:** `aws:MultiFactorAuthPresent` 条件キーでMFA認証済みセッションのみにアクセスを制限できる。
- **SCPはルートアカウントのIAMユーザーにも適用される** が、ルートアカウント自体(管理アカウント)にはSCPは適用されない。

## Well-Architected チェックリスト

### Security
- [ ] ルートアカウントにMFAが有効化されているか
- [ ] ルートアカウントのアクセスキーが削除されているか
- [ ] 全てのIAMユーザーにMFAが有効化されているか
- [ ] 永続的なアクセスキーの代わりにIAMロール(一時認証情報)を使用しているか
- [ ] パーミッションバウンダリーで権限の上限が設定されているか
- [ ] IAM Access Analyzerが有効化され、外部アクセスの検出が行われているか
- [ ] 未使用のIAMユーザー、ロール、ポリシーが定期的に棚卸しされているか
- [ ] クロスアカウントアクセスに外部ID (ExternalId) を使用しているか
- [ ] パスワードポリシーが適切に設定されているか (最低14文字、複雑性要件)
- [ ] CloudTrailが全リージョンで有効化され、IAM操作が記録されているか
